Q: A company runs a customer copilot on a Provisioned deployment. To save money, an engineer proposes scaling the PTUs up every morning at 8:00 and down every evening at 18:00 with a scheduled job. What is the main risk of this plan?
+ Capacity is not guaranteed when you scale back up, so the deployment may fail to scale at 8:00; use steady provisioned capacity with spillover for bursts instead :: Scaling down releases capacity back to the pool, and there is no promise you can get it back.
- Scaling PTUs up and down is blocked by Azure Policy by default :: No such default block exists; the risk is capacity, not policy.
- PTUs lose their quota each time they are scaled down :: Quota is a policy limit and is not consumed by scaling; capacity is the problem.
- Provisioned deployments cannot be changed after creation :: PTUs can be changed, but doing it daily is not a safe plan.
CONCEPT: A PTU (provisioned throughput unit) is a normalized slice of model capacity. Foundry reserves it for you and bills it hourly whether or not you send requests. Two ideas must be kept apart. Quota is a free policy limit on how many PTUs you may deploy. Capacity is the real hardware available right now for a model version. Having quota does not guarantee capacity.

When you delete or scale down, capacity returns to a shared pool. If you later scale up, the capacity may not be there, and the operation fails. That is why Learn advises against planning to scale up and down with daily traffic. Continuous hourly billing at high use also usually costs more than a reservation.

Better design: size provisioned capacity for the steady base load, and let spillover send bursts to a standard deployment.

Memory aid: quota is permission to rent; capacity is a car actually on the lot.

Q: A provisioned deployment returns HTTP 429 when it is full. The team enables spillover. Which statement describes how spillover works?
+ Overflow requests are redirected to a standard deployment in the same Foundry resource, for all requests or per request with the `x-ms-spillover-deployment` header :: This is the documented behavior for Azure OpenAI models.
- Overflow requests are sent to any deployment in any subscription of the tenant :: The target is a standard deployment in the same Foundry resource.
- Spillover doubles the PTUs of the deployment automatically :: It redirects traffic; it does not change PTU capacity.
- Spillover works for every model, including Llama and DeepSeek deployments from other providers :: Those deployments currently do not support spillover.
CONCEPT: A provisioned deployment has fixed capacity. When it is full it returns a non-200 status such as 429. The Provisioned Utilization metric (PTUs consumed divided by PTUs deployed) tells you when it is at or above 100%.

Spillover handles the overflow. When enabled, requests that the provisioned deployment cannot take are redirected to a standard (pay-per-token) deployment in the same Foundry resource. You can enable it for all requests or for one request with the `x-ms-spillover-deployment` header, which names the target.

This gives you a predictable base (provisioned, consistent latency) and an elastic top (standard, pay per use). Azure OpenAI models support it. Deployments of DeepSeek and Llama from other providers currently do not.

Spillover is a routing feature; it does not add capacity to the provisioned deployment.

Q: You size a Data Zone Provisioned deployment for `gpt-5.2`. Learn lists Input TPM per PTU = 3,400, output-to-input ratio = 8 and a scale increment of 5. Peak load is 600 requests per minute, with an average prompt of 500 tokens and an average response of 50 tokens. Forty percent of input tokens are served from the prompt cache. How many PTUs should you deploy?
+ 125 :: Input TPM 300,000 and output TPM 30,000. Normalized TPM = 300,000 x 0.6 + 8 x 30,000 = 420,000. 420,000 / 3,400 = 123.5, rounded up to the next increment of 5.
- 160 :: This ignores the cache rate (300,000 + 240,000 = 540,000; 540,000 / 3,400 = 158.8, rounded to 160).
- 55 :: This counts only the uncached input (180,000 / 3,400 = 52.9) and forgets the weighted output tokens.
- 124 :: This is the rounded value of 123.5 but not a valid size, because deployments scale in steps of 5.
CONCEPT: The documented formulas for sizing are:

Input TPM = peak RPM x average prompt size. Output TPM = peak RPM x average response size. Normalized TPM = Input TPM x (1 - cache rate) + output-to-input ratio x Output TPM. PTUs = Normalized TPM / Input TPM per PTU, then round up to the scale increment.

Here: Input TPM = 600 x 500 = 300,000. Output TPM = 600 x 50 = 30,000. Cached input is removed: 300,000 x 0.6 = 180,000. Output counts eight times: 8 x 30,000 = 240,000. Normalized = 420,000. Divide by 3,400 = 123.5. The increment is 5, so the answer is 125.

Notice that output tokens are the larger part (240,000 of 420,000) although there are ten times fewer of them. Newer model families use normalized token accounting where cached tokens consume capacity, so always read the sizing page for the model.

Q: A bank uses the standard agent setup. Three projects use Responses API agents and a fourth project uses only classic (Assistants-style) agents. All projects use the same Azure Cosmos DB account. Each Responses project needs 5 containers and the classic project needs 3 containers, each container with 1,000 RU/s. What total throughput must be provisioned for the agent data?
+ 18,000 RU/s :: 3 projects x 5 containers x 1,000 = 15,000, plus 1 project x 3 containers x 1,000 = 3,000.
- 12,000 RU/s :: This treats every project as classic (4 x 3 x 1,000).
- 20,000 RU/s :: This treats every project as Responses (4 x 5 x 1,000).
- 3,000 RU/s :: This is only the minimum account throughput, not the requirement for these projects.
CONCEPT: In the standard agent setup, conversations, agent definitions and run state live in your Azure Cosmos DB for NoSQL account. Each project needs 3 to 5 containers of 1,000 RU/s each. Three containers are created at provisioning, and up to two more appear when Responses API agents are used.

The rule gives a simple calculation. A project with Responses API agents needs 5 x 1,000 = 5,000 RU/s. A project with only classic agents needs 3 x 1,000 = 3,000 RU/s. Add them: 3 x 5,000 + 1 x 3,000 = 18,000 RU/s.

Too little throughput causes provisioning failures. The minimum account throughput is 3,000 RU/s, and both provisioned and serverless modes are supported.

Keep the Azure OpenAI resource, the Foundry account and the project in the same region, and give the Foundry account's managed identity the right Cosmos DB data-plane roles.

Q: You create a private endpoint for a Foundry resource and want names such as `myresource.openai.azure.com` and `myresource.services.ai.azure.com` to resolve to the private IP address inside your virtual network. Which set of private DNS zones do you link for the Foundry resource?
+ `privatelink.cognitiveservices.azure.com`, `privatelink.openai.azure.com` and `privatelink.services.ai.azure.com` :: These are the three zones listed for a Foundry resource.
- Only `privatelink.search.windows.net` :: That zone is for Azure AI Search.
- Only `privatelink.documents.azure.com` :: That zone is for Azure Cosmos DB for NoSQL.
- `privatelink.blob.core.windows.net` for all three endpoints :: That zone is for blob storage and does not resolve Foundry names.
CONCEPT: A private endpoint gives a service a private IP address inside your virtual network. But applications use names, not IP addresses. If the name still resolves to the public IP, traffic does not use the private endpoint. So private networking has two halves: the private endpoint, and DNS that returns the private address.

Each Azure service has its own private DNS zone names. For Foundry these are `privatelink.cognitiveservices.azure.com`, `privatelink.openai.azure.com` and `privatelink.services.ai.azure.com`. For Azure AI Search it is `privatelink.search.windows.net`, for Cosmos DB `privatelink.documents.azure.com`, and for blob storage `privatelink.blob.core.windows.net`.

Link each zone to the virtual network. If you use a custom DNS server, forward those zones to the Azure DNS virtual server `168.63.129.16`.

Test with `nslookup` from a VM inside the network: it must return a private address.

Q: After a database incident, a team wants to restore the Cosmos DB account used by the Agent Service. A restore creates a new account with the original name, but the restore fails. Which preparation was missing?
+ A unique, organization-specific account name, with continuous backup enabled before the incident :: A restore fails if the original name is taken, and point-in-time restore is unavailable unless continuous backup was enabled beforehand.
- A system-assigned managed identity on the Foundry project :: Learn recommends a user-assigned identity, but this does not cause a restore name conflict.
- A Provisioned deployment for the chat model :: Model capacity has nothing to do with restoring the data store.
- A larger virtual network address space :: Address space does not affect the name used by a restore.
CONCEPT: Foundry Agent Service has no built-in backup or point-in-time restore, so recovery depends on settings you configure before an incident. For Azure Cosmos DB: enable continuous backup (retention tiers of 7, 30 or 35 days) with point-in-time restore, which is unavailable unless it was enabled beforehand. Use a unique, organization-specific account name, because a restore creates a new account with the original name and fails if that name is taken. Add read replication to a failover region with service-managed failover.

The same name rule applies to Azure AI Search: use a unique, organization-specific service name. For storage, use GZRS for customer-managed failover. Use a user-assigned managed identity for the project so role assignments survive recreation, and the standard agent setup.

These checks are done in advance, not during the incident.

Q: A team put delete locks on its Cosmos DB account, Storage account and AI Search service. A few weeks later, an engineer with the Foundry User role deletes all conversation threads through the Agent Service API. Why did the locks not prevent this?
+ Locks protect the Azure resources, not the data inside containers, indexes or individual agents and threads; no built-in role is read-only for these operations :: Operational data can be deleted through the API, so standing delete permissions should not be granted.
- Delete locks only work on Sundays :: Locks have no schedule.
- Locks are removed automatically after 30 days :: Locks stay until someone removes them.
- Foundry User cannot delete anything, so the report must be wrong :: Even built-in roles such as Foundry User can delete operational data through the Agent Service APIs.
CONCEPT: A delete lock stops someone from deleting an Azure resource, for example the whole Cosmos DB account. It does not stop someone from deleting data inside the resource: documents in containers, entries in an index, or agents and threads removed through the Agent Service APIs.

Learn notes that even built-in roles such as Foundry User can delete operational data through those APIs, and no built-in AI role is read-only for them. So in production you should grant standing delete permissions to no one, use Azure Policy `denyAction` and delete locks on critical resources, keep continuous backup, and define agents as code so they can be recreated.

Locks need Owner to create. They are one layer of several.

Think of a lock as a padlock on the filing cabinet: it does not stop someone who has the key from shredding the papers inside.

Q: A regulated company uses hosted agents and requires customer-managed keys for all data. Which statement about customer-managed key (CMK) coverage is correct?
+ Hosted agents are only partly covered, because the `$HOME` filesystem is on platform-managed storage that is not encrypted with CMK :: Prompt agents support CMK only with bring-your-own storage, and hosted agents have this gap.
- Hosted agents are fully covered by CMK once the Foundry resource has a key :: Learn lists the `$HOME` filesystem as not encrypted with CMK.
- CMK for agents is configured only on the model deployment :: For agents, CMK is configured on the data stores such as Cosmos DB, Storage and AI Search.
- CMK replaces the need for Key Vault :: Keys are held in Azure Key Vault or Azure Managed HSM.
CONCEPT: Foundry supports customer-managed keys held in Azure Key Vault or Azure Managed HSM. You create or import a key, give the Foundry resource's managed identity permission to use it (with Azure RBAC on Key Vault this is the Key Vault Crypto User role), and then enable CMK on the resource, either at creation or later.

For agents the details matter. Prompt agents support CMK only with bring-your-own (customer-managed) storage, so you also configure CMK on Cosmos DB, Storage and AI Search. Hosted agents are only partly covered, because the `$HOME` filesystem is on platform-managed storage that is not encrypted with CMK.

If a compliance rule says "all data", the hosted-agent gap must be documented or a different design chosen.

Read the coverage list for the agent type you use before promising full CMK coverage.

Q: A security review finds a Foundry project that was created in the portal without private networking, while the approved design requires private endpoints. How do you prevent this in the future?
+ Create resources, projects, agents and connections from infrastructure as code, treat project creation as privileged, and enforce rules with Azure Policy :: Portal-created projects do not inherit network controls, and portal actions can bypass constraints.
- Ask developers to be careful when using the portal :: A process request is not an enforced control.
- Disable the network rules so that every project behaves the same :: This removes isolation instead of enforcing it.
- Give every developer the Owner role so they can fix settings :: Broad rights make unreviewed changes more likely.
CONCEPT: Governance works best when the setup is repeatable and enforced. Infrastructure as code (IaC) describes resources, projects, agents and connections in files that are reviewed and deployed by a pipeline. Learn gives reasons: portal actions run under a service identity and can bypass constraints, portal-created projects do not inherit network controls, and untracked portal edits cannot be reproduced.

So treat project creation as a privileged action, and combine IaC with Azure Policy. Policy can require private endpoints and network security groups, customer-managed keys and allowed regions, disable local (key) authentication, and restrict deployment types by denying `sku.name` on deployments.

For a locked-down environment, run the deployment pipeline from a self-hosted runner inside the network.

Rule: the portal is for exploring; code and policy are for production.

Q: An Application Gateway with WAF is the only internet-facing entry point to a chat application. The WAF blocks many legitimate chat messages as false positives because the text looks like attack patterns. What is the recommended handling?
+ Scope WAF exclusions to the chat message field, instead of disabling the rules :: This avoids false positives for that field while keeping protection elsewhere.
- Turn the WAF off completely :: This removes protection from the only internet-facing entry point.
- Disable all managed rules for the whole application :: This is too broad and weakens security.

Q: A security architect wants to stop a compromised agent from sending data to arbitrary internet addresses. The agent runs in an injected subnet. Which network design implements egress control?
+ A dedicated agent subnet with a user-defined route to Azure Firewall and FQDN allow rules :: Outbound traffic is forced through a firewall that permits only approved destinations.
- Public network access enabled on every dependency :: This opens more paths, not fewer.
- A shared subnet used by all workloads in the company :: The agent subnet is dedicated to one Foundry resource and cannot be shared.
- Removing the network security group from the subnet :: This removes a layer of control.
CONCEPT: Network isolation has an inbound side and an outbound side. Inbound traffic reaches Foundry through private endpoints with public access disabled. Outbound traffic from the agent runtime uses virtual network injection into a delegated subnet (delegated to `Microsoft.App/environments`).

Egress control limits where the agent may send data. The recommended design is a dedicated agent subnet with a user-defined route (UDR) that sends traffic to Azure Firewall, plus fully qualified domain name (FQDN) rules that allow only approved destinations such as Microsoft Entra endpoints. Network security groups on the subnet need matching outbound rules. Do not perform TLS inspection on agent traffic, because a substituted certificate breaks connections.

This is a defense for the case where the model is tricked: even if the agent tries to send data out, the firewall refuses.

Hosted agents also have network egress controls (Preview) with an allow-list of destinations.

Q: A GitHub Actions workflow deploys Foundry agents with the Azure Developer CLI. The current version stores a service principal secret as a repository secret and sometimes two runs deploy at the same time. Which two changes follow the recommended pattern?
+ Use GitHub OIDC federated credentials with `azure/login` and add a concurrency group that serializes deployments :: Federation removes the stored secret, and the concurrency group prevents two simultaneous deployments.
- Keep the secret but rotate it yearly, and let runs overlap :: The secret remains a stored credential, and overlapping runs can conflict.
- Use the project's API key in the workflow and run deployments in parallel for speed :: Keys bypass role-based access control, and parallel deployments can collide.

Q: A team's pipeline runs the full evaluation suite of 2,000 test cases with an LLM judge on every commit to every pull request. Costs rise and the pipeline slows down. Which change follows the guidance?
+ Run a small fast set (about a dozen cases) on every pull request and the full set only for release candidates :: This controls cost and still gates the release.
- Remove evaluation from the pipeline entirely :: Evaluation is the gate that catches regressions.
- Run the full suite on every commit but use a smaller judge model with no testing :: The judge model must be validated; the cost problem is the frequency.
- Replace the dataset with five easy cases :: A dataset that is too easy hides regressions.
CONCEPT: AI apps need evaluation as a gate in the pipeline, because quality can change without any code change. But evaluation costs money (model calls for the system and for the judge) and takes time.

Learn advises not running the evaluation Action on every commit, to control cost. A balanced design has two levels. A small, fast set of about a dozen cases runs on every pull request to catch obvious breaks. The full dataset runs on release candidates, before promotion to production.

Dataset hygiene helps both: version the dataset with the code, and add every production incident as a new case. A dataset that is too small or too easy produces a gate that always passes.

A gate should combine an absolute floor (for example safety defect rate at or below 1%) and a rule relative to the baseline.

Q: A team improves a prompt by editing five things at once: wording, examples, the output format, the temperature and the model. The score rises, and nobody knows why. Which approach does the prompt-improvement loop recommend?
+ Write a test set first, record a baseline, change one thing at a time, and keep a change only if the metric improves :: Single changes show cause and effect, and the baseline gives a reference.
- Keep all five changes because the score went up :: You cannot tell which change helped or hurt, and some may fail on other inputs.
- Tune only on the examples you can see in the prompt :: This overfits to the visible examples.
- Skip refusals in the test set to keep the score high :: A test for refusals is part of a good set.
CONCEPT: Prompt engineering is experimental work, so it needs a method. The loop has six steps. First, write the test: 30 to 50 real inputs with expected outcomes, including a few that should be refused. Second, run the simple prompt and record the baseline. Third, change one thing, such as adding an "out", adding two examples or adding a cue. Fourth, re-run and compare, keeping the change only if the metric improves. Fifth, review failures by hand, since each failure suggests the next change. Sixth, lock the prompt in version control together with its test results.

If you change five things together, you cannot tell which one helped, and one may have hidden a regression. Tuning on the visible examples only also overfits.

Common mistakes: no test for refusals, several changes at once, and judging by a few hand-picked examples.
SRC: https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/prompt-engineering

Q: A retrieval team compares chunking strategies for two content types: highly structured product specification tables and long narrative customer stories. Which guidance on overlap fits?
+ Use less overlap for highly structured data and more overlap for conversational or narrative text :: Narrative text depends on context across boundaries, while structured data usually stands alone.
- Use the same maximum overlap for every content type :: The guidance differs by content type.
- Use more overlap for structured data and none for narrative text :: This reverses the guidance.
- Never use overlap, because it only creates duplicates :: Overlap prevents an answer from being cut in half at a boundary, at the cost of extra storage and embedding calls.
CONCEPT: Chunking cuts text into pieces to stay under model token limits, to avoid one vector blurring many topics, and to return a focused passage to the model. The documented starting point is 512 tokens with 25% overlap (128 tokens).

Overlap is a trade-off. It repeats part of the previous chunk so that an idea that crosses a boundary is still intact in one chunk. This costs extra storage and embedding calls: with a 10,000-token document, 512-token chunks and 128 overlap, you get about 26 chunks instead of about 20.

The decision guide: larger chunks with overlap for questions about specific facts; less overlap for highly structured data; more overlap for conversational or narrative text; chunk by section for documents with headings; use semantic chunking with Content Understanding Markdown when you need meaning-preserving chunks across pages.

Always measure with retrieval evaluators on your own questions.

Q: A team asks when the semantic ranker is charged. They run many diagnostic queries with `search=*` and many production queries with `queryType=semantic` and a non-empty search string. Which queries generate semantic ranker charges?
+ Only queries with `queryType=semantic` and a non-empty search string :: The semantic ranker is a billed feature charged for those queries; an empty search is not charged.
- All queries, including `search=*` :: An empty search is not charged.
- Only queries that return captions :: Charging depends on the query type and search string, not on captions.
- No queries, because the semantic ranker is free in every plan :: It is billed, with a monthly allowance on the free plan.
CONCEPT: The semantic ranker is a second-stage reranker. It takes the top 50 results of BM25 or Reciprocal Rank Fusion, builds a summary string of up to 2,048 tokens for each from the fields of the semantic configuration, and scores each from 0 to 4 in `@search.rerankerScore`. It can also return captions and answers, which are always text copied from your index.

It is a billed feature. Charges apply when `queryType=semantic` and the search string is not empty. An empty search such as `search=*` is not charged. The free plan has a monthly allowance.

Because it only reorders what retrieval already found, it cannot rescue a document that is not in the first 50. Field order in the semantic configuration matters, since long text is trimmed. It works best on prose.

Do not set very fine thresholds on the reranker score: the distribution can shift with model updates.
SRC: https://learn.microsoft.com/en-us/azure/search/semantic-search-overview

Q: A vector field is indexed with HNSW. For one compliance audit the team wants exact nearest neighbors for a single query, without rebuilding the index. What can they do?
+ Set `exhaustive` to true on that vector query :: A field indexed for HNSW can still be queried exhaustively.
- Rebuild the field as HNSW with a lower `m` :: This is an indexing parameter that does not make search exact.
- Change the similarity metric to Euclidean :: The metric changes how distance is measured, not whether the search is exact.
- Lower `efConstruction` to 100 :: That lowers the build-time quality of the graph, which is the opposite of the goal.
CONCEPT: Vector search finds the nearest neighbors of a query vector. HNSW builds a layered graph at indexing time and walks it at query time, so it is fast but approximate. Exhaustive KNN scans every vector, so it is exact but slower.

HNSW has tuning parameters. `m` is how many neighbors each node links to. `efConstruction` is how many candidates are considered while building the graph (default 400, range 100 to 1,000). `efSearch` is the size of the candidate queue at query time. Higher values improve recall at a cost in time.

A field indexed for HNSW can still be queried exhaustively with `"exhaustive": true` on the vector query. The opposite is not possible: a field indexed as `exhaustiveKnn` cannot use HNSW.

This gives you a fast default and an exact option for audits or for building a ground-truth set to measure HNSW recall.

Q: A developer filters pure vector results with `@search.score >= 0.2` using the cosine metric, expecting to remove poor matches. Almost nothing is removed. What explains this?
