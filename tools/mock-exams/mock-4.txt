Q: A voice assistant uses a reasoning model for short intent classification, and users complain about a long pause before every answer. Accuracy is already high. Which change reduces latency the most?
+ Set `reasoning_effort` to `none` for this latency-critical task :: Reasoning models produce hidden reasoning tokens before the first visible token. A lower effort (or `none`) removes most of that wait.
- Add "think step by step" to the prompt :: This adds tokens and is not recommended for reasoning models.
- Increase `max_output_tokens` to 100,000 :: A larger cap does not make the model faster.
- Move the deployment to Batch :: Batch is asynchronous with a 24-hour target.
CONCEPT: Latency in a reasoning model comes mostly from the thinking phase. Before the first visible word, the model generates hidden reasoning tokens, and the user waits for them. The setting `reasoning_effort` controls how much it thinks.

Higher effort helps with hard multi-step problems. Short intent classification is easy, and accuracy is already high, so the extra thinking buys nothing. Setting `reasoning_effort` to `none` (where the model supports it) removes or minimizes the reasoning step, so the first token arrives much sooner. If `none` is not available for the model, use the lowest supported level and test accuracy again.

"Think step by step" does the opposite: it asks for more reasoning and is not needed for reasoning models. A bigger `max_output_tokens` only raises the cap. Batch is asynchronous with a 24-hour target, the opposite of low latency.

Memory aid: do not ask a professor to deliberate for ten minutes about a yes or no question.

Q: A product team plans to run a production workload on a model labeled Preview because it has the best benchmark results. Which risk should you point out, based on the model lifecycle?
+ Models move from Preview to GA, then Deprecated and Retired; production workloads need a GA model and a replacement plan, with notices and pinned versions :: When a model retires, deployments stop working, as happened with `dall-e-3` on March 4, 2026.
- Preview models are always more expensive than GA models :: Price is not the lifecycle risk.
- Preview models cannot be deployed in Foundry :: They can be deployed, but they are not meant for production.
- Benchmarks are invalid for Preview models :: Benchmarks exist but do not replace testing on your own data.
CONCEPT: Models and features have a lifecycle. A model starts as Preview, becomes generally available (GA), is later marked Deprecated, and finally Retired, after which deployments stop working.

Preview models can change, be limited in availability and quota, have no production SLA, and can be withdrawn with little time. A high benchmark score does not change that. Production workloads should run on a GA model, with a pinned version, an awareness of the retirement notices, and a plan for the replacement (evaluate the successor on your golden dataset before the retirement date).

The wrong statements: Preview models are not always more expensive, they can be deployed in Foundry, and benchmarks are not invalid for them.

This applies to any product: keep an inventory of models and features in use with their lifecycle stage and dates.

Q: You prepare the virtual network subnet for agent runtime injection in a Foundry resource. Which TWO requirements apply?
+ The subnet is delegated to `Microsoft.App/environments` and is dedicated to this Foundry resource :: Missing delegation causes provisioning failures, and the agent subnet cannot be shared between Foundry resources.
+ The Foundry resource is in the same region as the virtual network :: Other resources may be elsewhere, but the Foundry resource must match the VNet region.
- The subnet is shared with the application's virtual machines to save address space :: The agent subnet is dedicated per Foundry resource.
- The subnet overlaps with the peered on-premises network :: Overlapping ranges with peered networks are not allowed.
- The subnet is a /29 range :: A /24 is recommended and the minimum for portal injection is /27.
CONCEPT: Hosted agents and the agent runtime in a secured network use network injection: the runtime containers are placed into a subnet of your virtual network, so they can reach your private resources.

The subnet has strict requirements. It must be delegated to `Microsoft.App/environments`, which prepares it for the container environment, and it must be dedicated to one Foundry resource, since subnets cannot be shared between Foundry resources. The Foundry resource and the virtual network must be in the same region. The size matters too: /29 is far too small (the portal flow needs at least /27 and /24 is recommended), and the range must not overlap with peered or on-premises networks, because overlapping addresses cannot be routed.

Sharing the subnet with application virtual machines breaks the dedicated requirement.

Q: A chat application hits its tokens-per-minute limit at peak. Metrics show that most tokens are input tokens: a long system prompt, ten retrieved chunks and the full chat history are sent with every call. What should you do first?
+ Shrink the prompt: shorten the system prompt, send fewer or smaller chunks and summarize old turns :: Prompt tokens are most of the traffic, and trimming them is cheaper than quota or PTU.
- Buy Provisioned capacity immediately :: This is a larger commitment before checking the cheaper fix.
- Increase `max_output_tokens` :: Output is not the problem here.
- Retry every request three times :: More requests add more tokens and make throttling worse.
CONCEPT: Tokens-per-minute (TPM) limits count input and output tokens. Metrics show that most tokens are input tokens: a long system prompt, ten retrieved chunks and the full chat history are sent with every call. The cheapest fix is to send fewer tokens.

Shrink the prompt: shorten the system prompt; send fewer or smaller chunks (a reranker can select the best three instead of ten); summarize old turns instead of resending the entire history. Each change lowers input tokens per call, which lowers cost and latency as well, and gives headroom under the same limit. Prompt caching can discount the repeated stable prefix.

Buying provisioned capacity is a larger step and costs money every hour. Raising `max_output_tokens` increases the output cap, not input volume. Retrying makes more calls and consumes more tokens, which worsens throttling.

Q: A new deployment fails, and the Quota page shows 0 available for the model and deployment type. Another deployment in the subscription holds quota but is unused. What should you do?
+ Move quota from the unused deployment, or submit a quota increase request :: Both are documented ways to get more limit. Requests are evaluated individually.
- Buy a reservation :: A reservation is a discount and does not add quota.
- Add more custom headers to the request :: More than 10 custom headers returns HTTP 431.
- Wait for the quota to reset at midnight :: Quota is an allocation, not a daily counter.
CONCEPT: Quota is the amount of capacity your subscription may deploy for a model and deployment type in a region. When it shows 0 available, a new deployment cannot be created, even though the subscription's limit is shared with other deployments.

A reservation is a billing discount and does not create quota or capacity. Custom headers are irrelevant. Quota does not reset at midnight; tokens-per-minute rate limits renew every minute, but the deployment quota is a fixed allocation.

Q: You want to evaluate whether an agent used its tools efficiently compared with an expected sequence of tool calls, accepting `exact_match`, `in_order_match` or `any_order_match`. Which evaluator and prerequisite apply?
+ Task Navigation Efficiency, which needs ground truth (the expected sequence) :: It compares the agent's tool steps with an expected sequence.
- Tool Call Success, which needs no data :: It checks only whether a call technically succeeded.
- Intent Resolution, which needs a judge deployment only :: It checks whether the agent understood the user's intent.
- Customer Satisfaction, which compares with the system prompt :: It rates helpfulness, tone and resolution from the user's view.
CONCEPT: Agent evaluators measure different parts of the process. Some compare against expectations, so they need ground truth: a known correct answer or sequence.

Task Navigation Efficiency compares the actual sequence of tool calls with an expected sequence that you provide. It supports matching modes: `exact_match` (same steps, same order, no extras), `in_order_match` (the expected steps appear in the correct order, extra steps allowed) and `any_order_match` (all expected steps appear, in any order). Because it checks against an expected path, the prerequisite is the ground truth.

Tool Call Success needs no expected data: it checks whether tool calls ran without technical errors. Intent Resolution uses a judge model to rate whether the agent understood the request. "Customer Satisfaction" is not a built-in evaluator.

Q: A GitHub Actions pipeline deploys a hosted agent with the Azure Developer CLI. Which TWO practices follow the guidance?
+ Authenticate with GitHub OIDC federated credentials so that no secret is stored :: Federated credentials remove stored secrets.
+ Use a concurrency group so that two runs never deploy at the same time :: It serializes deployments.
- Store a service principal secret in the repository :: This is exactly what OIDC avoids.
- Skip evaluation because deployment succeeded :: The pipeline should fail the run when scores fall below thresholds.
- Run deployment manually from a laptop to stay flexible :: A pipeline gives repeatability and review.
CONCEPT: A reliable deployment pipeline has two requirements here.

Authentication with GitHub OIDC federated credentials: GitHub issues a short-lived identity token for the workflow, and Azure trusts it through a federated credential on an Entra app. There is no stored secret to leak or rotate. A service principal secret in the repository is the opposite.

A concurrency group: a GitHub Actions setting that allows only one run of the named group at a time. Without it, two pushes in quick succession start two deployments against the same environment, which can overwrite each other or fail.

Skipping evaluation because deployment succeeded confuses "it deployed" with "it works well": the agent may deploy successfully and still give worse answers. Deploying from a laptop removes review, repeatability and audit.

Typical pipeline: `azd provision`, `azd deploy`, then `azd ai agent eval run --no-prompt` that fails the job when scores fall below thresholds.

Q: A team wants to compare two agent versions with statistical confidence in a GitHub workflow and is worried about the cost of repeated evaluations. Which guidance applies to the evaluation GitHub Action?
+ List both agents as `name:version`; the first is the baseline by default; do not run it on every commit, to control cost :: Learn advises against running it on every commit and suggests running full evaluations on release candidates.

CONCEPT: The evaluation GitHub Action (preview, `microsoft/ai-agent-evals`) runs offline evaluations for Foundry agents inside a workflow. You identify agents as `agent-name:version`. Because versions are immutable, `support:3` and `support:4` are exact, comparable targets.

Evaluations call a judge model and run many test cases, so they cost money and time. Microsoft advises not to run it on every commit. Run it on pull requests that change agent behavior, on a schedule, or before release.

Passing only the agent name does not identify a version. And comparing agents is exactly what the Action is built for.

Q: Which statement about the risk and safety evaluators for harm categories (hate and unfairness, sexual, violence, self-harm) is correct?
+ Scores range from 0 to 7, the default threshold is 3, and a case passes if the score is less than or equal to the threshold :: A defect is a score above the threshold.
- Scores range from 1 to 5 and 3 fails :: The 1 to 5 range belongs to many LLM-judge quality evaluators.
- Scores are 0 or 1 only :: The harm evaluators return severity scores.
- A case passes only if the score is higher than the threshold :: The direction is reversed. A lower score is safer.
CONCEPT: Harm evaluators for Hate and unfairness, Sexual, Violence and Self-harm use a severity scale from 0 to 7. A higher score is worse.

The default threshold is 3. A case passes if its score is less than or equal to the threshold, and fails if it is greater. So a score of 3 passes, and 4 or more fails. This is easy to invert by mistake, because many quality scores (such as groundedness on a 1 to 5 scale) are better when higher.

You can change the threshold to match your risk tolerance. For a children's app you may use a lower threshold, such as 1, which fails anything above very low severity.

Remember the units: defect rate = failed cases divided by total cases. The scale of 1 to 5 belongs to quality evaluators such as groundedness, and 0 or 1 is not used for these harm scores.

Q: A prompt for a non-reasoning model asks it to decide which of three suppliers is cheapest after tax. Answers are sometimes wrong. Which technique should you add?
+ Chain of thought: ask for step-by-step reasoning before the final answer, in a fixed format such as "ANSWER is: <name>" :: It reduces errors and makes review easier on non-reasoning models.
- Raise the temperature to 1.5 :: More randomness reduces consistency.
- Remove all instructions :: The model needs clear instructions.
- Use `reasoning_effort=max` on the same non-reasoning model :: This setting belongs to reasoning models.
CONCEPT: Chain of thought is a prompting technique: ask the model to reason step by step before the final answer. For multi-step problems such as a price comparison after tax, writing the intermediate steps (compute tax for each supplier, then totals, then compare) makes errors less likely, because each step builds on visible text.

Put the final answer in a fixed format such as "ANSWER is: <name>", so your code can parse it and the reasoning can be ignored or logged.

Raising the temperature to 1.5 makes arithmetic less reliable. Removing instructions removes the task. And `reasoning_effort` applies to reasoning models, not to a non-reasoning model, so it cannot be set to max on it.

Reasoning models do this thinking internally, so for them the technique is not needed. That is the contrast the exam likes: classic chat model = ask for steps; reasoning model = keep the prompt short and goal-oriented.

Q: A fact-checking tool asks the model to "fact-check this paragraph" and the results are shallow. Which prompt-design change does Microsoft guidance suggest?
+ Break the task into two steps: first extract the factual claims, then write a search query for each claim :: Each step is easier to perform and to inspect.
- Make the prompt a single very long sentence :: Complexity hurts clarity.
- Tell the model never to be wrong :: This is vague and has no effect.
- Increase `max_output_tokens` :: A larger cap does not change how the task is structured.
CONCEPT: Complex tasks are often handled better when split into smaller steps (task decomposition). "Fact-check this paragraph" is vague: it asks the model to find claims, search, judge and report in a single leap, and the result is shallow.

A better design uses two prompts. Step 1: extract the factual claims from the paragraph, as a list. Step 2: for each claim, write a search query (and later check the evidence). Each step is simple, can be tested on its own, and the output of step 1 can be inspected and corrected.

A single long sentence makes the instruction harder to follow. "Never be wrong" cannot be obeyed. `max_output_tokens` only limits length.

This is also the base of agent workflows: small steps with clear inputs and outputs, with code or tools between them.

Q: A knowledge assistant's instruction says "Do not fabricate information", but reviewers still find invented facts. Which instruction change is more effective?
+ Ask for inline citations next to each claim, so an invented statement needs a false claim and a false citation, and checking becomes easy :: Citations make fabrication harder and verification simple. Closer citations work better than a list at the end.

Asking for inline citations changes the task. Each claim must come with a reference to a source passage, for example `[doc2]`. Removing the retrieved context removes the facts and makes invention more likely. Raising the temperature increases randomness.

Combine it with an "out" ("if the sources do not contain the answer, say you don't know") and a groundedness evaluation.

Q: Retrieval evaluators show low scores. Reading sample chunks, you find that each chunk covers many unrelated topics and ranks poorly for specific questions. Which step is at fault and what is the fix?
+ Chunking: the chunks are too large and their meaning is blurred; tune the size and overlap (for example start from 512 tokens with 25% overlap) :: Large chunks produce a vector that blends topics and a prompt full of noise.
- Generation: lower the temperature :: Generation cannot fix poor retrieval.
- Reranking: disable the semantic ranker :: The ranker cannot rescue a chunk that blurs meaning.
- Logging: store more traces :: Logs help diagnose but do not change retrieval.
CONCEPT: When retrieval quality is low, find which stage fails. Reading sample chunks is the right first diagnostic step. Here each chunk mixes many unrelated topics. An embedding of such a chunk is an average of several meanings, so it does not match any specific question strongly. It then ranks poorly.

The fault is chunking. Reduce the chunk size, split by sections or headings, and add overlap so boundary facts are kept. A documented starting point is 512 tokens with 25% overlap; then tune using retrieval metrics on labeled questions.

Lowering temperature affects generation, which is not where the problem is. Disabling the semantic ranker removes a helpful stage. Storing more traces helps debugging but does not change retrieval.

Memory aid: one chunk, one topic. A chunk that is a whole chapter is a bag of unrelated things.

Q: A RAG assistant should answer only when retrieval confidence is high and otherwise reply "not found". Semantic ranker scores range from 0 to 4. Which design is most appropriate?
+ Apply a score threshold on the reranker score (kept coarse, because score distributions can shift slightly) and return "not found" below it :: A relevance threshold raises precision at the cost of recall.
- Always answer and rely on a polite tone :: Low-confidence answers would still be shown.
- Use `orderby` to put the best document first :: Explicit sorting overrides relevance ranking.
- Set a very fine threshold such as 3.2137 :: Scores can shift slightly with infrastructure or model updates, so fine-grained thresholds are fragile.
CONCEPT: The semantic ranker gives each result a reranker score from 0 to 4. A threshold on this score is a simple confidence rule: if the best passage scores below the cut-off, there is probably no good answer, and the assistant replies "not found" instead of guessing.

Keep the threshold coarse, for example 2.0 or 2.5. Score distributions can shift slightly as the model, the index or the data change, so a very fine value such as 3.2137 gives false precision and breaks easily. Test the cut-off on labeled questions, including questions with no answer, and tune the balance between wrongly refusing and wrongly answering.

Always answering and relying on tone invites hallucination. `orderby` sorts results but does not tell you whether the best one is good enough.

Memory aid: set the pass mark at a round number and check it on real papers, not at 3.2137.

Q: Which similarity metric should you configure for a vector field that holds Azure OpenAI embeddings in Azure AI Search?
+ `cosine` :: It is the recommended metric for Azure OpenAI embeddings. The vector score for cosine is `1 / (1 + cosine_distance)`.
- `hamming` :: It is for binary vectors.
- Any metric, because the result is the same :: The metric must match how the embedding model was trained.
- `jaccard` :: It is a set similarity, not a vector metric in this configuration.
CONCEPT: A similarity metric defines how "closeness" between two vectors is calculated. Common ones are cosine (the angle between vectors), Euclidean (straight-line distance) and dot product.

Q: An indexer reads rows from Azure SQL Database. After the first run, edited rows are not picked up by later runs. What should you check?

CONCEPT: An indexer needs to know which source records are new or changed. For Azure Blob Storage this is automatic, because blobs have a last-modified timestamp that the indexer uses.
