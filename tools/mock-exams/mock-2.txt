Q: A customer-facing copilot runs 24 hours a day with high, steady traffic and a strict latency objective. Occasional bursts exceed the reserved capacity, and those requests must not fail. Which design fits best?
+ A Provisioned deployment with spillover to a Standard deployment in the same Foundry resource :: Provisioned gives reserved capacity and consistent latency for steady load. When it is full and returns 429, spillover sends the overflow to a standard deployment.
- A Global Standard deployment only :: Shared capacity is best effort. Heavy sustained use can show more latency variability and there is no latency target.
- A Batch deployment :: Batch is asynchronous with a 24-hour target and cannot serve interactive traffic.
- A Developer deployment :: It has no SLA and is meant only for evaluating fine-tuned models.
CONCEPT: Provisioned deployments reserve dedicated capacity, measured in PTUs (provisioned throughput units). The reservation gives predictable latency and throughput for steady traffic, but it has a fixed ceiling. When requests arrive faster than the reserved capacity can serve, the deployment answers 429 instead of queueing them.

Spillover solves the ceiling. You configure a standard (pay-per-token) deployment in the same Foundry resource as the overflow target. When the provisioned deployment is full, requests that would be rejected are served by the standard deployment instead. You can enable it for all requests on the deployment, or per request with the `x-ms-spillover-deployment` header. Clients keep calling the same endpoint, so no code changes.

The result is a cost-efficient design: the baseline load runs on reserved, predictable capacity, and only the bursts pay per token.

A Global Standard deployment alone gives no latency guarantee. Batch is asynchronous. Developer is for evaluating fine-tuned models and has no SLA.

Q: A team wants to host an open-source model that is not available as a serverless API, on dedicated GPUs, and bills per hour. Which statement about this option is correct?
+ It uses managed compute, which is billed per hour per accelerator SKU, and content filtering is not available in the preview :: Managed compute is for open-source, partner or custom models on dedicated GPUs. Learn notes that there is no content filtering in the preview, so you add your own safety layer.
- It uses a serverless standard deployment and bills per token :: Serverless APIs bill per use. Managed compute bills for the GPU time.
- It uses the Foundry Agent Service hosted agent runtime :: A hosted agent runs your code. It is not a way to host a model.
- It inherits the default guardrail `Microsoft.DefaultV2` automatically :: Content filtering is not available for managed compute in preview, so there is no guardrail unless you add one.
CONCEPT: Foundry offers several ways to run a model. Serverless (standard) deployments are hosted by Azure and billed per token. Managed compute is different: you rent virtual machines with GPUs that host the model for you.

Managed compute is used for open-source or custom models that are not offered as serverless APIs. You choose an accelerator SKU (the GPU VM size), and you pay per hour for each instance while it exists, whether or not requests arrive. You also need VM core quota for that SKU. In the preview described in the study material, content filtering (and so the default guardrail) is not applied automatically, so you add your own safety layer, for example by calling Content Safety.

Hosted agents are a different feature: a runtime for agent code that you build, not a way to host a model. Per-token billing belongs to serverless deployments.

Memory aid: serverless is a taxi (pay per ride); managed compute is a rented car (pay per day, even when parked).

Q: Security requires that nobody uses API keys to call a Foundry resource and that every call can be traced to a caller. Which TWO actions meet the requirement?
+ Use Microsoft Entra ID with managed identities and role assignments for callers :: Entra gives per-caller identity and role-based limits, with no secret to leak or rotate.
+ Use Azure Policy to disable key-based (local) authentication :: Policy enforces the rule for every resource, so keys cannot be used even by mistake.
- Store the keys in Azure Key Vault and rotate them monthly :: Keys are still shared full-access credentials that cannot identify who called.
- Share one key per team in a pipeline variable :: A shared key cannot tell individuals apart and gives full access.
- Give every developer the Foundry Owner role :: This grants broad privileges and does not remove key access.
CONCEPT: Authentication answers "who is calling". With API keys, anyone who holds the key is the caller, and nothing in the request says which person or app it was. With Microsoft Entra ID, each caller is an identity (user, app or managed identity), receives a short-lived token, and is allowed only what its role assignments permit. Logs then show the identity.

Meeting both requirements, no keys and traceable calls, needs two things. Use Entra ID with managed identities and give each caller a role (for example Azure AI User) at the right scope. And enforce the rule with Azure Policy, which can deny or audit resources that still have key-based (local) authentication enabled, across a whole subscription.

Keys in Key Vault with monthly rotation are better stored, but they are still keys and still shared secrets. One key per team in a pipeline variable is the opposite of traceable. Foundry Owner for everyone breaks least privilege.

Memory aid: a key is a house key anyone can copy; a role assignment is a named badge.

Q: A bank needs a network-secured Foundry Agent Service in which it owns the conversation data, uploaded files and vector stores. Which resources are required for the standard agent setup?
+ Azure Cosmos DB for NoSQL, Azure Storage and Azure AI Search, all with private endpoints :: Conversations and agent state go to Cosmos DB, files to Storage and file-search vector stores to AI Search. A network-secured standard setup requires all three.
- Only Azure Storage, because it can hold files and state :: Conversation state needs Cosmos DB and vector stores need AI Search.
- Azure SQL Database and Azure Cache for Redis :: These are not the BYO resources of the Agent Service standard setup.
- No extra resources, because the basic setup is already private :: The basic setup uses platform-managed storage and gives no ownership.
CONCEPT: Foundry Agent Service needs places to keep state. In the basic setup Microsoft manages that storage. In the standard setup you bring your own resources, so you own the data and can secure it with your own network rules and keys.

Storage alone cannot hold the conversation database or a search index. SQL Database and Redis are not the supported dependencies. The basic setup is not the "own your data" option, so "no extra resources" does not meet the bank's requirement.

Q: Two projects in one Foundry resource both use Responses API agents with the standard agent setup. Each project needs 3 to 5 Cosmos DB containers of 1,000 RU/s; three are created at provisioning and two more appear when Responses API agents are used. What is the minimum provisioned throughput to plan for?
+ 10,000 RU/s :: 5 containers x 1,000 RU/s x 2 projects = 10,000 RU/s.
- 6,000 RU/s :: This counts only the three provisioning-time containers, which applies to projects with classic agents only.
- 3,000 RU/s :: This is the minimum account throughput, not the requirement for these two projects.
- 5,000 RU/s :: This is the figure for one project, not two.
CONCEPT: Cosmos DB throughput is provisioned in request units per second (RU/s). Each project that uses the standard agent setup creates containers in your Cosmos DB account, and each container is provisioned at 1,000 RU/s.

The wrong answers each use a different container count: 3,000 = 3 containers for one project, 6,000 = 3 containers for two projects, and 5,000 = 5 containers for one project. When the question says "minimum to plan for" and "both projects use Responses API agents", use the maximum container count and multiply by the number of projects.

If the account is under-provisioned, conversation reads and writes are throttled with 429 responses, which users feel as failing chats.

Q: Every night, a job must classify 2 million support tickets. Results are needed by the next morning, and cost matters more than latency. Which deployment type should you use?
+ Batch (Global or Data Zone) :: Batch is asynchronous, has a 24-hour target and is billed at a discount of 50%, which fits large non-urgent jobs.
- Provisioned :: Reserved capacity is billed even when idle, and the job runs only a few hours per day.
- Priority processing :: It costs more to get faster responses, which the job does not need.
- Developer :: It is for evaluating fine-tuned models, not for production batch work.
CONCEPT: Batch deployments process large amounts of requests asynchronously. You upload a file where each line is one request, the service works through it in the background with a 24-hour target, and you download the results. In return you get a discount (about half the price) and a separate enqueued-token quota that does not use the quota of your online deployments.

Two million tickets overnight with the result needed the next morning is the textbook case: no user is waiting, volume is large, and cost matters more than speed. Global Batch may process anywhere; Data Zone Batch keeps processing in a zone when residency matters.

Provisioned reserves expensive capacity and is billed every hour, which is wasteful for a nightly job. Priority processing is a faster, higher-priced option for latency-sensitive calls. Developer is for evaluating fine-tuned models.

Q: An application sends a 3,000-token policy document plus a 40-token question on every request. The first message starts with a timestamp, and `cached_tokens` is always 0. How should you change the prompt to benefit from prompt caching?
+ Put the stable content (system message, policy document) first and the variable content (question, timestamp) last :: Caching needs an identical prefix of at least 1,024 tokens. A timestamp at the top changes the prefix on every call.
- Make the prompt shorter than 1,024 tokens :: A prompt must be at least 1,024 tokens to be cached.
- Switch to a Batch deployment :: Batch is cheaper but asynchronous. It does not make the prefix cacheable.
- Increase the quota :: Quota changes how much you can send, not how input tokens are billed.
CONCEPT: Prompt caching saves cost and latency when many requests start with the same text. The service remembers the already processed prefix of a prompt, and a later request that begins with an identical prefix of at least 1,024 tokens reuses that work. You can see it in the usage details: `cached_tokens` is above 0 on a hit.

The cache matches from the very first token. If the first message starts with a changing timestamp, the prefix is different on every request, so there is never a hit and `cached_tokens` stays 0. The fix is ordering: put stable content (system message, instructions, the 3,000-token policy) at the beginning, and variable content (the question, the timestamp) at the end.

Making the prompt shorter than 1,024 tokens disables caching. Batch is asynchronous and unrelated. More quota changes limits, not caching.

Result: the policy part becomes a cached discounted prefix, and only the 40-token question and timestamp are processed fresh.

Q: A bank's agent was told never to give investment advice. Reviewers find that in some conversations it recommends funds. Which evaluator measures whether the agent followed its system instructions and policy?
+ Task Adherence :: It checks that the agent follows its system instructions and policy, and catches advice the agent was told not to give.
- Tool Call Accuracy :: It checks whether the right tools were called with the right parameters.
- Task Navigation Efficiency :: It compares tool steps with an expected sequence to find needless calls.
- Tool Call Success :: It checks whether a tool call technically succeeded, such as API errors and timeouts.
CONCEPT: Agent evaluators check different parts of an agent's behavior, so you must pick the one that matches the question.

Task Adherence asks: did the agent follow its assigned task, instructions and policy constraints? Recommending funds when the system prompt forbids investment advice is a policy violation, so this is the right evaluator. Tool Call Accuracy and Tool Call Success look at tool calls: whether the calls were correct and whether they ran without technical errors. Task Navigation Efficiency compares the sequence of steps with an expected path and needs ground truth.

Other useful evaluators are Intent Resolution (did it understand the request), Task Completion (was the task finished) and Tool Output Utilization (did it use tool results correctly).

How it relates: run these on a test set before release, and on sampled production traffic after release, so rule-breaking behavior is caught as a number rather than by a customer complaint.

Q: An agent passed all pre-release evaluations. Three months later users complain about worse answers, although no code or prompt changed. Which practice would have detected this earlier?
+ Continuous evaluation of sampled production traffic and scheduled evaluation against a test set, with Azure Monitor alerts :: Quality can drift even when nothing changed, for example when data or the model behavior changes. Ongoing evaluation and alerts catch it.
- Running the pre-release evaluation again manually once a year :: The drift went unnoticed for months. A yearly check is too slow.
- Increasing the model's temperature :: Randomness does not detect problems.
- Turning off sampling to reduce cost :: Without sampling there is nothing to evaluate in production.
CONCEPT: Quality can fall without any code change: source documents become outdated, user questions shift, or a model version changes. This is called drift. Pre-release testing proves quality at one point in time and cannot see later changes.

Post-production monitoring has several layers. Continuous evaluation scores a sample of real production traffic all the time. Scheduled evaluation runs a fixed test set on a schedule (for example weekly), so results are comparable over time. Scheduled red teaming repeats attack tests. Azure Monitor alerts fire when a score crosses a threshold, so a person is told before users complain.

An annual manual run is far too rare. Temperature has no relationship to monitoring. Turning off sampling removes the data you need.

Example: the weekly golden-set run shows groundedness falling from 4.6 to 4.2 after the knowledge base was updated; the alert opens a ticket in week one instead of month three.

Q: A children's learning app must apply the strictest filtering for the violence category in its guardrail. Which severity threshold setting should you choose?
+ Low, which flags Low severity and above :: The threshold flags content at that level and above, so Low flags the most content and is the strictest setting.
- High, which flags only the most severe content :: High is the most permissive setting.
- Medium, because it is the default for all apps :: Medium flags Medium and above, which is less strict than Low.
- Off, because the model is already safe :: Off is only available to customers approved for modified guardrails and removes protection.
CONCEPT: Guardrail controls for harm categories have a severity threshold. The threshold says from which severity level the content is flagged and acted upon. Severity runs from safe through Low, Medium and High.

A lower threshold is stricter. "Low" flags content of Low severity and above, so it catches almost everything, including mild content. "Medium" flags Medium and High. "High" flags only the most severe content and lets the rest through. "Off" removes the check.

A children's app wants the strictest filtering, so it selects the lowest threshold, Low. The cost is more false positives: some harmless content may be blocked, which is an acceptable trade-off for this audience.

The default setting is not the same for all apps, and "the model is already safe" is not a basis for turning controls off. Always test the chosen thresholds with real examples to find a balance between safety and usability.

Q: A team wants to find prompt-injection and jailbreak weaknesses in its agent that nobody has thought of, before release and again every month afterward. What should they use?
+ The AI Red Teaming Agent (PyRIT-based), run before release and on a schedule :: It generates adversarial attacks and scores the target by risk category. Attackers adapt, so scheduled runs after release matter too.
- A fixed evaluation dataset of known questions, run once :: It only replays known cases and cannot find new attack paths.
- A higher guardrail threshold on the output :: This reduces what is shown but does not discover weaknesses.
- A diagnostic setting on the resource :: Logs record what happened. They do not probe for weaknesses.
CONCEPT: Evaluation with a fixed dataset only finds problems that someone already imagined. Attackers are creative, so you also need a tool that invents new attacks.

The AI Red Teaming Agent is built on PyRIT, Microsoft's open-source framework for red teaming generative AI. It generates adversarial prompts across risk categories, transforms them with attack strategies (for example encodings, character flipping or multi-turn pressure), sends them to your agent or model, and scores the answers with safety evaluators. The result is an attack success rate per category. Run it before release and then on a schedule, for example monthly, because the agent, the model and the attacks change. Add human red teaming for creative, domain-specific tests.

A fixed dataset run once is a snapshot. A higher output threshold does not find weaknesses. A diagnostic setting only records logs.

Memory aid: a fixed test is a fire drill; a red team is a friendly arsonist.

Q: In a CI/CD pipeline, a candidate agent version has a task adherence score of 4.4 with a 95% confidence interval of 4.3 to 4.5. The production version scores 4.6. The absolute floor in the gate is 4.0. What should the gate decide?
+ Fail, because the whole interval lies below the production baseline, even though the score is above the floor :: A relative-to-baseline rule catches regressions that an absolute floor hides.
- Pass, because 4.4 is above the floor of 4.0 :: This uses only the absolute rule and hides the regression.
- Pass, because helpfulness improved :: One improved metric does not offset a regression in a critical one.
- Skip the gate, because the interval is wide :: The interval is narrow and entirely below the baseline.
CONCEPT: A release gate should not rely only on an absolute number. It should combine an absolute floor with a comparison against the current production version, using statistics.

Task adherence is scored on a scale (here about 1 to 5). The candidate's mean score is 4.4 and the 95% confidence interval is 4.3 to 4.5. A confidence interval is the range in which the true value probably lies. Production scores 4.6, which is above the whole interval, so the candidate is very probably worse. It passes the floor of 4.0, but a floor alone would let a real regression through.

So the gate fails. An improvement in a different metric such as helpfulness does not cancel a regression in a critical metric. A wide interval is a reason to run more test cases, not to skip the gate.

Memory aid: the floor stops disasters; the baseline comparison stops slow decline.

Q: A chat application stores conversations through Foundry Agent Service. A tester discovers that changing the conversation ID in a request returns another user's conversation. What is missing?
+ An application-level check that the caller owns the conversation; Foundry does not enforce per-user access to conversations :: Without ownership checks the application has a broken object-level authorization flaw.
- A stronger model deployment :: Model strength has nothing to do with authorization.
- Public network access on the Foundry resource :: This opens more access and does not add ownership checks.
- A longer conversation ID :: IDs are identifiers, not a security control.
CONCEPT: Authentication proves who the caller is. Authorization decides what that caller may access. Foundry Agent Service enforces access to the project and its agents with roles, but it does not know which of your end users owns which conversation.

If the app lets the browser send a conversation ID and the backend simply forwards it, a user can change the ID and read someone else's data. This is an insecure direct object reference (IDOR). The fix is in your application: store which user owns each conversation, and before every call check that the signed-in user owns the ID. Better, never accept raw IDs from the client; look them up from the user session on the server.

A stronger model does not enforce access. Public network access makes it worse. A longer ID only hides it and is not a control.

Memory aid: the hotel gives every guest a room key, but it is the front desk logic that checks you are going to your own room.

Q: You build a RAG assistant. Sometimes it invents an answer when the retrieved context does not contain the information. Which prompt design reduces this most directly?
+ Give the model an "out": instruct it to answer only from the context and to reply "not found" when the answer is missing, and repeat the instruction at the end :: An explicit safe answer avoids invented ones, and repeating key instructions near the end uses the recency effect.
- Increase the temperature so that the model is more creative :: This increases invention.
- Remove the retrieved context to keep the prompt short :: Without context the model answers from memory.
- Ask the model to "never hallucinate" in capital letters :: A vague instruction is weak. A concrete rule with an allowed fallback works better.
CONCEPT: Language models try to be helpful, so when the context lacks the answer they often produce a plausible one. This is a hallucination.

The most direct prompt fix is to give the model an "out": a clear, allowed way to say it does not know. For example: "Answer only from the context below. If the answer is not in the context, reply `not found`." Repeating the rule at the end of the prompt helps because models pay extra attention to the most recent text, so a rule buried at the top of a long prompt can fade.

Increasing temperature makes invention more likely. Removing the context removes the facts and makes things worse. Writing "never hallucinate" in capitals is not a mechanism; the model needs a concrete alternative behavior.

Also test it: include evaluation cases where the answer is absent and check that the model says "not found", for example with a groundedness evaluator.

Q: A prompt asks the model for search queries but returns several queries when you need exactly one. Which prompt technique from the Microsoft guidance fixes this with the least change?
+ Prime the output with a cue, for example ending the prompt with "One possible search query is:" :: A cue is the start of the answer. It steers the form of the output, here to a single query.
- Add 20 few-shot examples of unrelated tasks :: Unrelated examples add tokens and do not constrain the output form.
- Set `top_p` and `temperature` to the maximum :: This makes output more random.
- Switch the deployment to Batch :: Batch is a billing and latency choice. It does not change the answer shape.
CONCEPT: Priming the output means starting the model's answer for it. You end the prompt with the first words of the desired response, so the model continues in that format instead of choosing its own.

Here the prompt asks for search queries and the model lists several. Ending the prompt with a cue such as "One possible search query is:" makes the natural continuation a single query. This is a small change, with no extra examples and no change of parameters.

Few-shot examples are a different technique, they show input and output pairs. They can help, but 20 examples of unrelated tasks add cost and noise. Setting `top_p` and `temperature` to the maximum increases randomness, which makes extra queries more likely. Switching to Batch does not change the format.

Memory aid: priming is like giving a speaker the first word of the sentence; they will usually finish it the way you wanted.

Q: You design chunking for a 10,000-token document before embedding. Which TWO statements are correct?
+ A documented starting point is 512 tokens with 25% overlap (128 tokens) :: This is the recommended starting point to test on your own data.
+ Overlap prevents an answer from being cut in half at a chunk boundary, at the cost of more chunks and embedding calls :: With a 384-token stride the document produces about 26 chunks instead of about 20 without overlap.
- Larger chunks are always better because they keep more context :: Large chunks blur meaning, cost more and may exceed token limits.
- One vector for the whole document gives the best retrieval :: A single vector blurs many topics together.
- Chunking is unnecessary because embedding models accept unlimited input :: Embedding models have input limits, for example 8,191 tokens for `text-embedding-3-small`.
CONCEPT: Chunking splits long documents into pieces before embedding. An embedding model has an input limit, and a single vector for a whole document blurs many topics into one point, so retrieval is poor.

Microsoft's documented starting point is chunks of 512 tokens with 25% overlap, which is 128 tokens shared between neighboring chunks. Overlap repeats the end of one chunk at the start of the next, so a fact or sentence that falls on a boundary appears whole in at least one chunk. The trade-off is more chunks, more embedding calls and a larger index. Tune size and overlap with your own questions and evaluation scores.

"Larger is always better" is false: big chunks dilute the meaning and cost more tokens in the prompt. "One vector per document" and "no chunking" fail on long files.

For a 10,000-token document at 512 tokens with 128 overlap, each new chunk moves forward by 384 tokens, which gives about 26 chunks.

Q: A RAG pipeline ingests scanned PDFs. Search returns nothing for content that is clearly on the pages, and the extracted text of those files is empty. Which step failed and what is the fix?
+ Text extraction: a scanned PDF has no text layer, so add OCR (or Content Understanding / Document Intelligence Layout) to the pipeline :: Without OCR there is nothing to chunk or embed. Checking the extracted text of a few real files finds this quickly.
- Reranking: enable the semantic ranker :: The ranker reorders results that exist. Here the content was never extracted.
- Generation: lower the temperature :: Generation cannot use text that was never indexed.
- Embedding: switch to `text-embedding-3-large` :: A better embedding model cannot embed text that does not exist.
CONCEPT: RAG pipelines have stages: extract text, chunk, embed, index, retrieve, rerank, generate. If an early stage produces nothing, later stages cannot recover.

A scanned PDF is a picture of pages. It has no text layer, so a normal text extractor returns an empty string, and there is nothing to chunk or embed. The symptom "search returns nothing for content that is clearly on the page" together with "extracted text is empty" points straight at extraction.

The fix is to add OCR. In Azure AI Search, use an indexer with the OCR skill on normalized images, or use Document Intelligence Layout or Content Understanding, which read scanned pages and return text and structure (often as Markdown). Then chunk and embed that text.

Q: You need to measure the recall of an approximate nearest-neighbor (HNSW) vector index. Which approach is documented?
+ Run exhaustive KNN queries on the same data to create a ground-truth set, then compare the HNSW results with it :: Exhaustive KNN scans all vectors for exact results, so it is the ground truth for measuring HNSW recall.
- Raise `efConstruction` to 1,000 and assume recall is 100% :: Tuning parameters improves recall but does not measure it.
- Enable the semantic ranker and compare scores :: The ranker scores relevance of text, not the recall of a vector index.
- Use `euclidean` instead of `cosine` :: The metric must match the embedding model. Changing it does not measure recall.
CONCEPT: KNN (k-nearest neighbors) means finding the k items most similar to a query. In vector search, each document is stored as a list of numbers (an embedding), and the query is turned into the same kind of list. KNN compares the query with every stored vector, measures the distance to each, and returns the k closest. Because it checks everything, the result is exact. The cost is that it gets slow as the collection grows to millions of vectors.

HNSW (Hierarchical Navigable Small World) is a faster way to find nearby vectors that accepts a small chance of error. It builds a graph in which each vector links to some of its neighbors, arranged in layers. The top layer has a few long-range links, like highways between cities, and the lower layers have more short-range links, like local streets. To search, the algorithm enters at the top, hops to whichever linked vector is closest to the query, and drops down a layer whenever it gets stuck. This skips most of the vectors, so it is much faster. Because it follows links instead of checking everything, it can occasionally miss a true nearest neighbor. That is why it is called approximate.

How they relate. KNN is the exact method and is the reference answer. HNSW is the fast approximate method used in practice. Recall measures how often HNSW finds the same neighbors that exact KNN finds. In this question, you run both on the same data, treat the KNN results as the correct answers, and see how many of them HNSW also returns.

A simple way to remember it: KNN checks every house in town to find the closest one, and HNSW uses a map of highways and streets to get near it quickly and then checks the nearby houses, which is usually close enough.

Q: For the review "The room was clean but the staff were rude", a hotel wants to know that the room is positive and the staff are negative. Which capability provides this?

- Language detection :: It returns the language of the text only.
- Extractive summarization :: It selects important sentences and does not assign sentiment to aspects.
CONCEPT: Ordinary sentiment analysis gives one label (positive, neutral, negative) for a whole sentence or document. That cannot express "the room is good, the staff are bad" in the same sentence.

Opinion mining, also called aspect-based sentiment analysis, goes deeper. It finds the targets (aspects) that people talk about, such as "room" and "staff", and the opinion words attached to them ("clean", "rude"), and assigns sentiment to each target. For the example: room is positive, staff is negative.

Key phrase extraction lists the main phrases and does not score sentiment per target. Language detection returns the language. Extractive summarization selects important sentences.

Use opinion mining when the business needs to know what exactly people like or dislike, for example to report on rooms, staff, location and price separately.

Q: A product owner wants a summary made of the most important original sentences of a long support article, with a rank score and sentence positions, and no newly written text. Which type of summarization is this?
+ Extractive summarization :: It selects the most important original sentences and returns rank scores and positions.
- Abstractive summarization :: It writes new sentences.
- Key phrase extraction :: It returns phrases, not sentences.
- Opinion mining :: It assigns sentiment to aspects and does not summarize.
CONCEPT: Summarization has two main styles.

Extractive summarization selects the most important sentences from the original text and returns them unchanged. Each selected sentence comes with a rank score and its position (offset), so you can highlight it in the source. No new text is written, so nothing is invented.

Abstractive summarization writes new sentences that paraphrase the content, like a human summary. It reads more smoothly but can introduce errors, and there is no sentence position to point to.

Key phrase extraction returns short phrases, not sentences. Opinion mining returns sentiment about targets.

The requirement here is "the most important original sentences", "rank score and sentence positions" and "no newly written text". Each clue points to extractive summarization.
