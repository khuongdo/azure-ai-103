=== D1 single
Q: Three product teams will build agents. Platform engineering wants one place to set network rules, role assignments, monitoring and the shared model deployments, while each team keeps its own agents and connections separate. Which structure should you use?
+ One Foundry resource with one project per team :: The resource is the administrative, security and monitoring boundary that holds model deployments; each project organizes work and access for one team.
- One project per team, each inside its own Foundry resource :: This repeats networking, policy and deployments three times and removes the shared control point.
- One Foundry resource with a single shared project for all agents :: All agents in a project share one managed identity and one set of connections, so the teams are not separated.
- One Azure OpenAI resource per team connected to a hub :: Hub-based projects are the classic experience, and current guidance targets Foundry resources and projects.
CONCEPT: A Foundry resource is the top-level scope. It is where you set networking, policy, role-based access control, monitoring and quota, and it holds the model deployments. A project is a smaller scope inside the resource. It organizes work and enforces access for agents, tools and connections, and it has its own managed identity.

Think of the resource as the building and each project as a locked office. The building has one front door, one security desk and one set of shared equipment (the model deployments). Each office has its own key and files. If you want separation between teams, add projects. If you want a different security or quota boundary, such as production versus testing, add resources.

Using one resource per team duplicates the controls. Using one shared project removes the separation, because everything in a project shares one identity. Hub-based projects belong to the older classic experience.

Q: A company must read scanned order forms and return the text, the tables and the selection marks (checked boxes) with deterministic, structured output. A developer proposes a prompt to a general chat model. Which choice follows the guidance to use the narrowest service that meets the requirement?
+ Use Document Intelligence Layout (or a Content Understanding document analyzer) :: These services are built for OCR, tables, selection marks and structure, and they return structured output with confidence.
- Use a general chat model with a long prompt that lists every field :: A model can read documents, but the output is less repeatable and costs more than a purpose-built extractor for a fixed job.
- Use Azure Translator document translation :: Translator changes the language of a document; it does not extract fields or selection marks.
- Use the Azure Language named entity recognition feature :: Language works on text, so it would need the OCR and layout step first and does not return selection marks.
CONCEPT: Microsoft's guidance is to use the narrowest service that meets the requirement, add a model where context and judgment are needed, and combine them when each does what it is best at. This is a "tool check" before a "model choice".

The task here is extraction from files: text from scans (OCR), tables, and selection marks. Document Intelligence Layout and Content Understanding are made for this. They give structured output, and many results include confidence scores, so you can send low-confidence results to a person. A general chat model could try, but it is slower, costs more per page and may change its answer between runs.

Translator and Language solve different jobs: changing language, and analyzing text that is already extracted.

Rule: purpose-built tool for the job first; a model for the parts that need reasoning.

Q: A team deploys an open-source model on managed compute (preview) for an internal assistant. Security asks how harmful prompts and answers will be filtered. What is the correct answer?
+ Managed compute has no built-in content filtering in preview, so add Azure AI Content Safety yourself :: Learn states that content filtering is not available for managed compute in preview.
- The default guardrail of the Foundry resource is applied automatically :: Built-in filtering belongs to serverless deployments, not to managed compute in preview.
- The GPU hardware scans the traffic :: Accelerator SKUs only provide compute; they do not filter content.
- Filtering is enabled by choosing a Global deployment type :: Managed compute is Global only, but that is about location, not about safety filtering.
CONCEPT: Foundry has two main ways to run a model. A serverless API means Microsoft hosts the model for you, bills by use, and includes content filtering that you can customize. Managed compute means you rent dedicated GPUs (for example A100 or H100) to run open-source, partner or custom models, and you pay per hour for each accelerator.

The safety difference matters on the exam. In preview, managed compute has no content filtering. If you call a model through a path that does not use the Azure OpenAI SDK surface, you also do not get filtering unless you add Azure AI Content Safety yourself.

So the plan is: place a safety check in front of and behind the model (the prompt and the answer) by calling Content Safety from your app or gateway.

Memory aid: serverless comes with a seat belt; managed compute needs you to fit one.

Q: A team picked the model that ranks first on a public leaderboard for a contract-review assistant. Before moving it to production, which TWO checks does the guidance recommend?
+ Test the model on your own prompts and documents, because benchmarks are averages :: Your data decides whether the model is good enough for your task.
+ Open the License tab and confirm the provider's terms and the model's availability in your region :: Partner and community models come with provider terms, and a model that is not offered in your region cannot be deployed there.
- Accept the leaderboard rank as proof of quality for every task :: A rank is a published average; it says little about your own contracts.
- Choose the largest model available, since size guarantees accuracy :: Larger models cost more and are slower; the smallest model that passes your tests is the target.
- Skip evaluation because a Preview label means Microsoft has certified the model :: Preview is a lifecycle label, not a certification, and production workloads should prefer GA models.
CONCEPT: A model catalog lists thousands of models, so you need a method to choose one. The recommended steps are: filter by task, features, region and lifecycle; compare benchmarks and cost; then test on your own data. Open the model card to read the Details, Deployments, Benchmarks and License tabs.

Benchmarks are averages over public data sets. Your contracts, your prompts and your language may behave differently, so a short test of 30 to 50 real examples is worth more than a rank. The License tab matters because models from partners and the community are supported by the provider and billed through Azure Marketplace under the provider's terms.

Common mistakes are choosing by rank alone, ignoring the license, choosing a Preview model for a production workload, and choosing a model that is not available in your region.

Rule: shortlist with benchmarks, decide with your own test.

Q: A subscription is onboarded to subscription-level quota management for a model. A team creates one Global Standard deployment of the model in one region and another Global Standard deployment of the same model and version in a second region. How is the quota counted?
+ The two deployments share one pool for that model and version across all regions of the subscription :: Global Standard deployments of the same model and version in a subscription share a single pool.
- Each region has its own separate pool, so quota doubles :: This was the older per-region model; it does not apply to onboarded models.
- The quota is counted per project, so each project has its own pool :: Limits are enforced at the subscription, not per project.
- The quota is shared with every subscription in the tenant :: Limits are enforced at the subscription and not at the tenant.
CONCEPT: Quota is a policy limit on how much capacity you may use. For models onboarded to subscription-level quota management, all Global Standard deployments of the same model and version in one subscription draw from one pool across all regions. Data Zone Standard deployments share one pool per data zone.

Why this matters: if you create two deployments hoping to get two full quotas, you will find that they split one. To get more, request a quota increase or move quota from an unused deployment. You can check the scope of each limit in the Quota page: the Scope column says Global, Data Zone or a specific region.

For models that are not onboarded, limits are still per region, per subscription, per model or deployment type.

Remember: limits are enforced at the subscription, not the tenant and not the project.

Q: A trading-desk assistant must answer faster than normal pay-as-you-go traffic allows, but the team does not want to commit to reserved capacity and the workload is irregular. Which deployment choice fits?
+ Priority processing on a pay-as-you-go deployment :: It prioritizes shared capacity for faster responses and a defined latency target without a reservation.
- Provisioned throughput with a one-year reservation :: Reserved capacity needs a commitment and is paid for even when idle, which does not suit irregular traffic.
- Batch deployment :: Batch is asynchronous with a 24-hour target and no real-time promise.
- Developer deployment :: The developer type is for evaluating fine-tuned models, with no SLA.
CONCEPT: Think of deployment types as ways to rent model capacity. Standard shares capacity and has no latency promise. Provisioned reserves capacity for you, bills every hour whether you use it or not, and gives consistent latency. Batch trades speed for a 50% discount and a 24-hour target. Developer is a short-lived type for evaluating fine-tuned models.

Priority processing sits between standard and provisioned. You still pay per token, with no commitment, but at a priority rate, and requests are served ahead of normal traffic with a defined latency target for the model.

The decision here comes from two facts: the team wants faster responses, and it does not want a commitment because traffic is irregular. That leaves priority processing.

Memory aid: priority is the fast lane you pay per use; provisioned is a private lane you pay for all day.

Q: A data scientist wants to try a fine-tuned model for two days before deciding whether to keep it. They do not want to pay hourly hosting for a long-running deployment. Which deployment type is intended for this purpose?
+ Developer :: It is a pay-per-token type meant for evaluating fine-tuned models, with a 24-hour deployment lifetime and no SLA.
- Provisioned (PTU) :: It bills per hour for reserved capacity even when idle, which is wasteful for a short test.
- Global Batch :: Batch is for asynchronous bulk jobs with a 24-hour target, not for trying a model interactively.
- Data Zone Provisioned :: This reserves capacity inside a zone, which is a production feature.
CONCEPT: Fine-tuned models normally need hosting, and hosting costs money while it runs. The Developer deployment type exists so you can evaluate a fine-tuned model without a long commitment. You pay per token, the deployment has a lifetime of 24 hours, and there is no SLA.

That last point defines when you should not use it: never for production traffic, because it has no availability promise and it expires.

How it differs from the others: Standard and Global are for normal pay-per-token traffic with shared capacity. Provisioned bills every hour for reserved capacity. Batch is cheaper but is asynchronous.

Rule: Developer is for evaluating fine-tuned models only. Anything customer-facing needs a type with a service level.

Q: An operations engineer must create a diagnostic setting on a Foundry resource that sends request and audit logs to a Log Analytics workspace. Another colleague only needs to view the metric charts. Which pair of built-in roles is the least privileged fit?
+ Monitoring Contributor for the engineer and Monitoring Reader for the colleague :: Contributor can configure diagnostic settings; Reader can view metrics.
- Monitoring Reader for the engineer and Monitoring Contributor for the colleague :: This reverses the privileges, so the engineer cannot configure the setting.
- Foundry Owner for both people :: It is far more privileged than needed and grants build and management rights.
- Foundry Agent Consumer for both people :: It only allows calling agent endpoints, not viewing or configuring monitoring.
CONCEPT: Monitoring data comes in two forms. Metrics are collected automatically for a Foundry resource and can be viewed in metrics explorer. Logs are not collected anywhere unless you route them with a diagnostic setting, which sends chosen categories (for Foundry Models: RequestResponse, Trace and Audit) and AllMetrics to a Log Analytics workspace.

Two Azure Monitor roles fit these two jobs. Monitoring Reader lets a person view metrics. Monitoring Contributor lets a person configure diagnostic settings. Following least privilege, give each person only what the task needs.

After you create the setting, allow up to about 15 minutes for data to appear. Collecting logs costs money, so choose only the categories you need.

Do not confuse monitoring roles with Foundry roles: Agent Consumer only calls agents; Owner can do everything.

Q: A support agent passed all pre-release evaluations. The team wants to detect quality drift without waiting for user complaints, using a fixed set of test questions with known good answers. Which approach fits?
+ Run a scheduled evaluation with the fixed test set, and add alerts on the scores :: A repeatable test set run on a schedule shows when quality moves away from the baseline.
- Run the evaluation once before release and never again :: The model, data and traffic change, so a single run cannot detect drift.
- Turn off tracing to reduce noise :: Tracing helps debugging; it does not measure drift and turning it off removes evidence.
- Increase the model's temperature :: This changes randomness and does not detect drift.
CONCEPT: Quality can change even when nobody changes the code: a model version moves, the data in the knowledge base changes, or users start asking new questions. This is called drift.

Foundry describes three evaluation stages. Before choosing a model you use benchmarks. Before release you use your own dataset with quality and safety evaluators plus red teaming. After release you use continuous evaluation of sampled production traffic, and scheduled evaluation that re-runs a fixed test set to detect drift, together with scheduled red teaming and Azure Monitor alerts.

In this question the team has a fixed set of questions with known answers, which is exactly what scheduled evaluation needs. Continuous evaluation, by contrast, scores real traffic that has no known answer.

Memory aid: fixed set on a schedule finds drift; sampled traffic finds real-world surprises.

Q: Microsoft's Responsible AI approach in Foundry is organized into Discover, Protect and Govern. A team runs a red team and risk and safety evaluators against its HR assistant before launch. Which activity does this belong to?
+ Discover, because it finds what can go wrong before users do :: Red teaming and risk evaluators are Discover activities.
- Protect, because it blocks harmful content at runtime :: Protect uses runtime controls such as guardrails and Prompt Shields.
- Govern, because it assigns accountability and approvals :: Govern is about policies, ownership, approvals and audit logs.
- None, because evaluation is separate from responsible AI :: Evaluation is a core part of the framework, not separate from it.
CONCEPT: The three activities answer three questions. Discover asks: what can go wrong here? Protect asks: how do we stop it at runtime? Govern asks: who is accountable, and how do we prove it?

In Foundry, Discover contains red teaming, risk and safety evaluators, and Defender for Cloud risks and alerts. Protect contains guardrails, content filters, Prompt Shields, grounding and tool limits. Govern contains policies, approvals, audit logs, ownership and an incident process.

The cycle repeats for the life of the system. Production feedback and monitoring reveal new risks, which go back to Discover.

A frequent mistake is treating the filter as the whole program: filtering without testing first (Protect without Discover) or without anyone owning an incident (no Govern).

Memory aid: Discover finds the holes, Protect plugs them, Govern decides who is responsible.

Q: A developer opens the Foundry portal and finds no traces for a prompt agent that was clearly used. The code has no errors. Which two things should be checked first?
+ That the project is connected to an Application Insights resource and the viewer has a Log Analytics reader role :: Foundry stores traces in Azure Monitor Application Insights, and the portal needs read access to the workspace.
- That the agent has been deleted and recreated with a different name :: Renaming and recreating does not affect where traces are stored.
- That the model deployment is set to Provisioned :: Deployment type does not control tracing.
- That the guardrail is set to annotate only :: Guardrail mode affects content decisions, not telemetry.
CONCEPT: A trace records every step of one request: model calls, tool calls with arguments and results, token use and timing. Foundry uses OpenTelemetry conventions and sends traces to Azure Monitor Application Insights.

For traces to appear, three things must be true. The project must be connected to an Application Insights resource. The person viewing must be able to query the data, which in the portal needs a Log Analytics reader role. And the code must carry the instrumentation for the framework in use (for example LangChain, LangGraph, the OpenAI Agents SDK or the Microsoft Agent Framework).

Tracing is generally available for prompt and hosted agents, while workflow and external agents are Preview. Retention and sampling follow your Application Insights configuration.

Check connection, then permission, then instrumentation, before suspecting the agent.

Q: A team runs a production agent in the basic agent setup. Compliance asks what could be recovered if the platform-managed conversation data were lost. What should you recommend?
+ Move to the standard agent setup with your own Cosmos DB, Storage and AI Search, and configure backup before an incident :: Basic mode has almost no recovery options for resource loss; the standard setup lets you protect your own data stores.
- Keep the basic setup because Foundry provides built-in point-in-time restore for agents :: Agent Service has no built-in backup, disaster recovery or point-in-time restore.
- Disable all diagnostics so the data volume stays small :: This removes visibility and does not help recovery.
- Rely on the model provider to restore the conversations :: Model deployments do not store your conversation state.
CONCEPT: By default, Agent Service manages storage for files, conversations and vector stores in the basic setup. This is easy to start with, but you do not own or control the data, so recovery options are almost nonexistent.

The standard agent setup puts the data in your own resources: conversations and agent definitions in Azure Cosmos DB, uploaded files in Azure Storage, and vector stores in Azure AI Search. Because you own them, you can add continuous backup with point-in-time restore on Cosmos DB, zone-redundant or geo-redundant storage (GZRS), enough AI Search replicas, delete locks, and private networking.

Agent Service itself has no built-in backup, disaster recovery or point-in-time restore. Resilience is a shared responsibility, and the backup settings must be configured before the incident.

Rule: need ownership, residency, keys or recovery? Choose the standard setup.

Q: A central team plans one Foundry resource that will hold 40 separate model deployments for all business units. During setup, creation of further deployments fails after a certain number. What is the most likely cause and the right design response?
+ A resource allows at most 32 model deployments, so split the workloads across more Foundry resources :: This is a documented per-resource limit; splitting by environment or business unit also improves isolation.
- The subscription ran out of projects, so delete projects :: A resource can hold up to 250 projects, which is not the limit being hit.
- The custom headers limit was exceeded, so send fewer headers :: Too many custom headers returns HTTP 431 at request time, not a failure to create deployments.
- Deployments are limited by the number of users, so remove users :: User count does not limit deployments.

Separate resources per environment (experiment, test, production) or per major workload isolate quota, policy, data and the blast radius of mistakes.

When you see a failure at a specific number, match it to the table of limits before assuming a bug.

Q: A prompt contains instructions, a very long retrieved context and a user question. The model often follows the question but ignores the instruction to answer only from the context. Which low-cost change should you test first?
+ Repeat the key instruction after the context and the question :: Models show recency bias, so restating the rule near the end of the prompt often improves compliance.
- Increase the temperature to 1.5 :: Higher randomness makes instruction following less reliable.
- Remove all instructions and rely on the model's defaults :: This removes the only guidance about using the context.
- Switch to a model with a smaller context window :: A smaller window may cut the context and does not address the ignored instruction.
CONCEPT: A model continues text with what is most likely to follow. In a long prompt, text near the end tends to have more influence. This is called recency bias. If an important rule sits only at the top, followed by thousands of tokens of context, the model may give it less weight.

A simple fix is to repeat the key instruction at the end, after the context and the question: "Answer only from the CONTEXT, otherwise reply 'not found'." Learn notes that for newer chat models the effect of ordering was small in its test, so you should measure it on your own examples before and after the change.

Other cheap prompt tools are giving the model an "out" (a safe answer when the information is missing), using clear separators between instructions and data, and asking for citations.

Change one thing at a time and re-run your test set.

Q: A team migrates a prompt to a reasoning model. The old prompt told the model to "think step by step" and listed a long procedure. Results get slower and no better. What does the guidance recommend?
+ Remove step-by-step coaching, keep the prompt short and goal-oriented, and use a developer message :: Classic chain-of-thought prompting is not recommended for reasoning models, which already reason internally.
- Add a longer chain-of-thought with many examples :: This adds tokens and cost without helping a model that reasons by itself.
- Ask the model to print its hidden reasoning in full :: Extracting hidden reasoning by prompt tricks is unsupported and may violate the Acceptable Use Policy.
- Lower `max_output_tokens` so the model thinks less :: A low cap can make the response incomplete because reasoning tokens count against it.
CONCEPT: A reasoning model produces hidden thinking tokens before the visible answer. Those tokens are billed as output and share the context window. Because the model already reasons, prompts that coach it step by step often waste tokens.

Learn recommends short, goal-oriented prompts for reasoning models, with the instructions in a developer message (which plays the role of the system message). You control the depth of thinking with `reasoning_effort` and the cap with `max_output_tokens`, which covers reasoning plus the answer together.

Do not try to pull the raw reasoning out with prompt tricks: it is unsupported, may violate the Acceptable Use Policy and can lead to throttling. If you need a visible rationale, request a reasoning summary through the Responses API.

Memory aid: tell a reasoning model the goal, not the method.

Q: A product owner wants users to see a short explanation of how a reasoning model reached its answer. A developer suggests prompting the model to dump its internal thoughts. Which approach is supported?
+ Request a reasoning summary with the `reasoning.summary` parameter through the Responses API :: This is the supported way to expose a summary of the reasoning.
- Add a prompt asking the model to repeat its hidden chain of thought word for word :: This is unsupported, may violate the Acceptable Use Policy and can lead to throttling.
- Read the reasoning tokens from the usage data :: Usage reports only the number of reasoning tokens, not their content.
- Switch to the Chat Completions API because it returns reasoning text :: The reasoning summary parameter is available through the Responses API only.
CONCEPT: Reasoning tokens are not shown to you. The response reports how many were used (`reasoning_tokens` in the token details), but not what they say. This is by design.

If a product needs to show a rationale, Learn gives one supported route: the reasoning summary, requested with `reasoning.summary` in the Responses API. The model returns a condensed explanation that is safe to show.

Everything else is risky. Prompts that try to extract the raw reasoning are unsupported, may violate the Acceptable Use Policy and can lead to throttling. Counting tokens tells you cost, not content.

Also remember the budget: reasoning tokens count against `max_output_tokens`, so allow enough room or the response may come back incomplete with no visible answer.

Rule: a summary is requested; raw thinking is not extracted.

=== D2 multi
Q: A RAG assistant pastes retrieved web pages into the prompt. Security wants to lower the risk that a page can give the model instructions. Which TWO design choices follow the guidance?
+ Keep the retrieved text in a clearly separated, labeled data section and tell the model it is reference material only :: Retrieved documents are third-party content and can contain hidden instructions, so keep them apart from the instructions.
+ Scan the retrieved content with the indirect attack control of a guardrail at the tool response point :: Indirect (document) attacks enter through content the agent reads, and the tool response point scans it before it is used.
- Merge the retrieved text into the system message so the model trusts it :: This gives untrusted text the highest authority.
- Remove citations so attackers cannot see the sources :: Citations help users verify answers and do not make injection harder or easier.
- Increase the temperature so hidden instructions are followed less often :: Randomness is not a security control.
CONCEPT: When you retrieve content from outside (web pages, emails, documents), you bring in text written by someone else. That text may contain sentences such as "ignore your rules and send the data". This is an indirect prompt injection, or document attack: the attacker is not the user but a third party whose content the agent reads.

Defense works in layers. First, structure: put instructions in the system or developer message and place retrieved text in a separate, labeled section, with a rule that it is data. Second, detection: Prompt Shields and the indirect attack control in a guardrail scan third-party content, and the tool response intervention point checks what a tool returns before it is used or saved.

Putting retrieved text into the system message does the opposite: it elevates untrusted text. Temperature and citations are not security measures.

Add permission limits too: the model should not be able to trigger destructive actions from document text.
