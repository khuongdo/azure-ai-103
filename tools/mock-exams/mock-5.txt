Q: A retail chatbot must serve 10,000 concurrent chat sessions with low latency and low cost. Answers are short FAQ-style replies, and there is no residency requirement. Which design is the best starting point?
+ A small model on a Global Standard (or Standard) pay-per-token deployment :: A smaller model reduces both latency and cost per token, and pay-per-token fits a workload that has not shown a need for reserved capacity.
- The largest available model on Provisioned capacity :: It raises cost and latency, and PTU pays off only for steady, high, proven volume.
- A reasoning model with `reasoning_effort=high` :: Hidden reasoning tokens add latency and cost to simple FAQ replies.
- A Batch deployment :: Batch has a 24-hour target and cannot serve live chat.
CONCEPT: Choose a model and deployment type from the workload, not from the biggest numbers. The workload here has many concurrent users, short FAQ-style answers, a need for low latency and low cost, and no residency requirement.

Small models are faster and cheaper per token, and they are good enough for short, well-defined replies, especially with retrieval for the facts. A Global Standard (or Standard) pay-per-token deployment charges only for use and scales with a shared pool, which suits a retail pattern with peaks. If the load later becomes steady and high, or the latency target becomes strict, evaluate Provisioned.

The largest model on Provisioned is expensive and unnecessary for FAQ answers. A reasoning model with high effort adds hidden thinking, latency and cost. Batch is asynchronous, so a live chat cannot use it.

Rule: start with the smallest model that passes your evaluation, and move up only when measurements show a gap.

Q: An executive asks why the company's resilience design for model deployments uses Data Zone and Global types instead of plain Standard. Which answer is correct?
+ Standard deployments are single-region with no availability-zone support, while Data Zone and Global types spread processing over more capacity :: Resilience also needs a gateway and spillover, because Foundry does not fail deployments over by itself.
- Standard deployments replicate to every region automatically :: They are single-region.
- Global types guarantee that data at rest is stored in any region :: Data at rest stays in the designated geography. Only inference processing location differs.
- Data Zone types remove the need for any gateway :: Foundry does not load-balance deployments, so a gateway is still recommended.
CONCEPT: Resilience depends on where a deployment runs. A Standard deployment is tied to a single region and does not support availability zones. If that region has a problem, capacity runs out, or traffic spikes, the deployment has nowhere to move to.

Data Zone and Global deployment types route requests across more capacity: Data Zone inside a geography such as the EU or the US, Global over all supported regions. That adds headroom and availability and lowers the chance of throttling. Global does not mean storage everywhere: data at rest is tied to the resource location. Standard does not replicate to every region automatically.

Even with those types, you still need a gateway for health checks, failover to another deployment and circuit breaking, because Foundry does not load-balance or fail over deployments for you. So Data Zone does not remove the need for a gateway.

Memory aid: Standard is one road; Data Zone and Global are a road network.

Q: You configure private networking for a Foundry resource, Azure AI Search and Azure Cosmos DB. Which TWO statements about private DNS are correct?
+ Link private DNS zones such as `privatelink.search.windows.net` and `privatelink.documents.azure.com` to the virtual network :: Without linked zones, names still resolve to public IPs.
+ A custom DNS server should forward these zones to the Azure DNS virtual server `168.63.129.16` :: This lets custom DNS resolve the private endpoint addresses.
- Private endpoints for Storage, AI Search and Cosmos DB are created automatically by the standard agent setup :: They are not auto-created, so you create them yourself.
- One private DNS zone name works for every service :: Each service has its own zone name.
- Private endpoints work without any DNS configuration :: Name resolution must return the private IP.
CONCEPT: Private networking has two halves: the private endpoint (a private IP for the service) and DNS (the name that resolves to that IP). DNS is where most setups break.

Each Azure service has its own private DNS zone name, for example `privatelink.search.windows.net` for Azure AI Search and `privatelink.documents.azure.com` for Cosmos DB (NoSQL). You must create these zones and link them to the virtual network, so that machines in the network resolve the service names to private IPs. If you use a custom DNS server, it should forward queries for those zones to the Azure-provided DNS at `168.63.129.16`, which knows the private zones.

Private endpoints for dependencies are not created automatically; you create them. There is no single zone name for all services. And without DNS configuration, the name still resolves to the public IP, so the private endpoint is not used.

Test: `nslookup` from a VM in the network should return a private address.

Q: A security architect reviews outbound rules for an agent subnet. The firewall team proposes TLS inspection on all agent traffic. What should you advise?
+ Do not perform TLS inspection on agent traffic, because a substituted certificate breaks connections; allow Microsoft Entra endpoints (or the AzureActiveDirectory service tag) instead :: This is documented guidance for firewalls in front of the agent runtime.
- Enable TLS inspection and trust the firewall certificate in the agent runtime :: Learn advises not to inspect agent traffic.
- Block all Entra endpoints to reduce exposure :: Agents need Entra for authentication.
- Disable the firewall for the agent subnet :: Egress control is a requirement against data exfiltration.
CONCEPT: Agent subnets carry traffic from the agent runtime to Microsoft services and your resources. A firewall team often wants TLS inspection (decrypting and re-encrypting traffic to look inside). With TLS inspection, the firewall presents its own certificate instead of the service's certificate. The agent runtime does not trust that substituted certificate, so connections fail.

The guidance is therefore: do not perform TLS inspection on agent traffic. For security you can still control the traffic by destination: allow the Microsoft Entra endpoints (or the `AzureActiveDirectory` service tag), which the agent needs to obtain tokens, and restrict other outbound traffic with allow-lists.

Blocking Entra endpoints would stop token acquisition, and the agent could not authenticate at all. Disabling the firewall removes control instead of tuning it. Trusting the firewall certificate inside the agent runtime is not a supported option.

Memory aid: let the courier carry sealed envelopes; checking by destination is fine, opening them breaks the seal.

Q: Even built-in roles such as Foundry User can delete operational data through the Agent Service APIs, and accidental deletion of dependencies could cause catastrophic loss. Which combination of controls is recommended?
+ Delete locks on critical resources, Azure Policy `denyAction`, and no standing delete permissions for anyone in production :: Locks need Owner to create, and they do not protect data inside containers, indexes or individual agents and threads, so permissions matter too.
- Delete locks only, because they protect data inside containers :: Locks do not protect the data inside containers, indexes, agents or threads.

Combine them with backups: Cosmos DB continuous backup and agent definitions in source control.

Q: A team has two immutable agent versions in production, `support:7` and `support:8`. After the release of version 8, task adherence drops. They want to return to the previous behavior quickly. Which statement is correct?
+ Versions are immutable, so rollback means pointing traffic back at `support:7`; canary and blue-green routing need a routing layer that you build :: Foundry does not provide canary routing, and an existing version never changes.
- Edit version 7 in place and redeploy it as 9 :: Versions never change. A change creates a new version.
- Foundry shifts 5% of traffic to the new version automatically :: Canary routing must be built by you.
- Delete the agent and recreate it with the same name :: A saved agent's name cannot change, and deleting loses history.
CONCEPT: Agent versions are immutable: any change creates a new version, referenced as `name:version`. The old version remains available. That makes rollback simple: point your callers back at `support:7`. You do not edit version 7 in place (it cannot be edited), and you do not delete the agent, which would lose history and invalidate IDs.

Foundry does not shift traffic gradually between versions by itself. Canary releases (for example 5% on version 8, 95% on version 7) and blue-green switching need a routing layer that you build, such as an API gateway or application logic with configuration for the version name.

Procedure after the drop in task adherence: switch traffic to version 7, keep version 8 for investigation, compare the two on the same golden dataset to find what regressed, fix and release as version 9.

Memory aid: versions are saved photographs; rollback is hanging the old photograph back on the wall.

Q: A reasoning-model call needs a long answer. A developer wants to know what budget to start with so that the answer is not cut by reasoning. What does Learn suggest?
+ Reserve at least 25,000 tokens for reasoning plus output at first, then tune down from measured `reasoning_tokens` :: The cap covers reasoning and visible output together, and logging the 95th percentile of reasoning tokens tells you the cap to set.

Q: A long prompt contains instructions, a lengthy retrieved context and a user question, and the model sometimes ignores the rule at the top. Which two prompt-design practices help?
+ Use clear separators or labeled sections (Markdown or XML), and repeat the key instruction at the end of the prompt :: Models show recency bias, and clear syntax separates instructions from data.
- Put the rule only in the middle of the context :: This is the least visible position.
- Remove all separators to save tokens :: Separators clarify structure and can serve as stop conditions.
- Use random capitalization to draw attention :: It does not provide structure.
CONCEPT: A long prompt has several parts, and models do not weigh every part equally. Text in the middle of a long context can be overlooked, and rules at the very top can fade.

Two practices help. Use clear separators: label sections with Markdown headings or XML-like tags such as `<instructions>`, `<context>` and `<question>`, so the model can tell instructions from data. And repeat the key instruction at the end of the prompt, close to where the answer starts, because models pay extra attention to recent text.

Putting the rule only in the middle of the context hides it among the data. Removing separators saves a few tokens but mixes instructions and data, which also raises injection risk. Random capitalization is not a technique.

Structure also helps security: marking retrieved content as data makes it easier to tell the model not to follow instructions inside it.

Q: An answer generator drafts reports, and errors are costly. The team designs a reflection loop. Which description is correct?
+ Generate a draft, critique it against explicit criteria, revise using the critique, and stop after a fixed number of rounds or when the criteria pass; check objective criteria (valid JSON, citation present) with code instead of a model :: Each round adds a call, so reflection trades cost and latency for quality.

A loop that repeats until the model says it is happy can run forever and burn tokens. Reflection is not free: each round is another model call with more tokens and latency, so use it only where errors are costly, like these reports.

Q: An agentic retrieval request must be fast and cheap for simple lookups, but still handle complex questions when needed. Which setting controls whether an LLM plans subqueries?
+ The retrieval reasoning effort: `minimal` skips LLM query planning, and `low` (the default) or `medium` use an LLM to split the question into subqueries :: Lower effort reduces cost and latency.
- The number of replicas of the search service :: Replicas add capacity but do not change planning.
- The chunk overlap :: Overlap is an indexing setting.
- The vector profile name :: It selects an algorithm for a vector field.
CONCEPT: Agentic retrieval can plan its own queries, but planning costs time and money. The retrieval reasoning effort controls this.

With `minimal` effort, the service skips LLM query planning: it runs the query directly across the knowledge sources and returns grounding data. That is fast and cheap, good for simple lookups. With `low` (the default) or `medium` effort, an LLM reads the question and conversation, splits the question into focused subqueries, runs them in parallel and merges the results, which handles complex multi-part questions better.

Replicas affect capacity and availability, chunk overlap affects how documents are split at indexing time, and a vector profile name selects an algorithm for a field. None of them switches the planning step.

Design idea: route by difficulty. Use minimal for short keyword-like queries and a higher effort when the question has several parts or depends on earlier turns.

Note that planning and synthesis are available in the preview API version, not in the GA minimal mode.

Q: A search service stores 50 million vectors, and the vector index size quota is nearly exhausted. The data is queried by approximate search. Which statement about vector algorithms and quota is correct?
+ HNSW keeps all vectors in memory and uses vector index size quota, while exhaustive KNN uses none, but it scans all vectors and suits small to medium data :: Choose the algorithm by data size, accuracy need and quota.
- Exhaustive KNN uses more quota than HNSW :: It uses none.
- HNSW uses no memory because it reads vectors from disk on every query :: HNSW stores vectors in memory.
- A field indexed as `exhaustiveKnn` can use HNSW at query time :: It cannot.
CONCEPT: Vector indexes need memory and disk, and the algorithm decides which. HNSW (Hierarchical Navigable Small World) is the approximate algorithm: it builds a graph of vectors that is kept in memory for fast traversal. Therefore HNSW vectors count against the vector index size quota of the search service. Exhaustive KNN does not build such an index in memory; it compares the query with every stored vector, so it uses none of that quota, but each query scans everything and becomes slow as data grows. It suits small to medium collections, or the use of ground-truth checks.

With 50 million vectors and a nearly exhausted quota, the choice is not trivial: moving to exhaustive KNN would make queries too slow, so you would look at compression (quantization), fewer dimensions, a larger service tier or partitioning.

A field is configured for one algorithm in its profile. A field indexed for exhaustive KNN does not become HNSW at query time, and HNSW does not read vectors from disk on every query.
