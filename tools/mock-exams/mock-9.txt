Q: A risk and safety evaluation of a wellbeing chatbot shows the model sometimes infers a user's emotional state or other protected traits that the conversation never stated. Which evaluator is built to detect this?
+ Ungrounded attributes :: It detects inferring protected traits, such as an emotional state, that are not present in the context.
- Protected material :: It detects copyrighted text or code in the output.
- Code vulnerability :: It detects insecure patterns in generated code.
- Violence :: It scores violent content in the output.
CONCEPT: Risk and safety evaluators run in the hosted Foundry Evaluation service, so you do not deploy a judge model. They cover several kinds of risk. Hate and unfairness, Sexual, Violence and Self-harm score harm categories from 0 to 7 (default threshold 3; a case passes if its score is at or below the threshold). Protected material finds copyrighted text or code. Code vulnerability finds insecure patterns in generated code. Ungrounded attributes finds inferences of protected traits that are not present in the context. Indirect attack finds attacks hidden in content. Prohibited actions and Sensitive data leakage (both Preview) are for agents.

Ungrounded attributes matches this case: the chatbot "guessed" something about the user that the conversation never said. The risk is both accuracy and fairness.

Match the symptom to the evaluator name before choosing: each one answers a different question.

Q: A coding assistant generates SQL and shell snippets that developers paste into production scripts. A reviewer is worried that the generated code may contain insecure patterns. Which evaluator should be added to the pre-release safety suite?
+ Code vulnerability :: It detects insecure patterns in generated code.
- Task Navigation Efficiency :: It compares tool steps with an expected sequence.
- Customer Satisfaction :: It rates whether a user would be satisfied.
- Groundedness :: It checks that answers stay inside the supplied context.
CONCEPT: Safety is more than offensive text. For an assistant that writes code, a major risk is that the code itself is unsafe, for example building SQL by string concatenation or running shell commands with unchecked input. The Code vulnerability evaluator looks for insecure patterns in generated code, and it is part of the risk and safety group together with Protected material, Ungrounded attributes, Indirect attack and the harm category evaluators.

Use it in the pre-production stage: build a dataset with normal and adversarial requests ("write a login query"), run the evaluators and the red teaming agent, set a pass rule such as a maximum defect rate, and make it a release gate. A defect rate is the share of test cases that fail.

After release, continue with sampled continuous evaluation and alerts. Code review by people remains important, because evaluators are aids and not guarantees.

Q: A research agent reads web pages and emails. Testers want an evaluator that detects attempts hidden in content, such as manipulated content, intrusion and information gathering. Which evaluator targets these?
+ Indirect attack (XPIA) :: It detects attacks hidden in content that the system reads.
- Hate and unfairness :: It scores hateful or unfair content.
- Protected material :: It finds copyrighted material.
- Response Completeness :: It measures recall of expected facts.
CONCEPT: Two attack families matter for generative systems. A user prompt attack comes from the user: change the system rules, embed a fake conversation, role-play a persona without limits, or hide the request with encoding. An indirect (document) attack comes from a third party: a document, email, web page or tool result carries hidden commands. Its goals include manipulated content, intrusion (access to system infrastructure), information gathering, availability attacks, fraud and malware.

For measurement, the Indirect attack evaluator (XPIA) checks for such attempts. For prevention at runtime, Prompt Shields and the guardrail control for indirect attacks scan user input and tool responses. The AI Red Teaming Agent, which uses the PyRIT framework, generates attacks that the team did not think of.

The three pieces form a loop: Discover (evaluators and red team), Protect (guardrails) and Govern (policy and ownership).

Q: A finance agent calls tools that return customer records. Reviewers worry that the agent may expose sensitive data in its replies or intermediate tool calls, and that judging only the final answer is not enough. Which evaluator (Preview) is meant for agents in this situation?
+ Sensitive data leakage :: It checks whether an agent exposes sensitive data.
- Fluency :: It scores the language quality of text.
- Tool Output Utilization :: It checks whether the agent used the tool result correctly.
- Task Completion :: It checks whether the task finished with a usable deliverable.
CONCEPT: Agents add risks that plain chat does not have. They call tools, read third-party content and act. Two risk evaluators are made for agents and are in Preview: Prohibited actions (agent actions outside policy) and Sensitive data leakage (the agent exposing sensitive data).

A common mistake is judging only the final answer. An agent can leak data in an intermediate tool call and then give a clean-looking final answer. Evaluating the full set of messages, including tool calls and results, finds this.

Combine the evaluator with runtime controls: tool call controls in the guardrail look at what the agent proposes to send to a tool, least-privilege identities limit what it can reach, and approvals protect high-impact actions. Add the failing cases to the test suite so the gate stays strict.

Use Preview features with care and re-check their status before relying on them.

Q: A team ran a red teaming exercise once before launch and considers the safety program finished. Which statement matches the guidance on the AI Red Teaming Agent?
+ Run it before release and again on a schedule after release, together with continuous evaluation of sampled production traffic :: Attackers adapt, and models, prompts and data change, so testing must repeat.
- One run is enough because attacks never change :: Attackers adapt, so a single run goes stale.
- It replaces all human review and needs no oversight :: It is best used with human review.
- It only checks spelling mistakes :: It simulates attacks and scores results by risk category.
CONCEPT: A fixed evaluation dataset replays questions you already know. Attackers invent new ones. The AI Red Teaming Agent simulates attacks, using Microsoft's PyRIT framework (jailbreaks, prompt injection and more), and scores the target by risk category such as hate or violence. It is best used with human review.

Timing matters. Run it before release. Then run it on a schedule after release (scheduled red teaming), and pair it with continuous evaluation of sampled production traffic and Azure Monitor alerts. Re-run it after any change to the model, the prompts, the tools or the guardrails, because each change can open a new gap.

In the Discover, Protect and Govern framework, red teaming belongs to Discover, and what it finds feeds Protect (new controls) and Govern (incident process and ownership).

Memory aid: a fire drill once is not a fire safety program.

Q: A grocery chain lets an agent reorder low-risk stock automatically. Volume is high and each action is cheap to undo. Managers do not want to approve each action but want to be able to step in. Which oversight pattern fits?
+ Human on the loop: monitor and intervene when needed :: This fits low-risk, high-volume actions.
- Human in the loop: approve every action before it runs :: This suits hard-to-reverse, high-impact actions and would not scale here.
- No oversight at all :: Even low-risk automation needs monitoring and an escalation path.
- Human after the fact only, with yearly audits :: A yearly audit is too slow for operational issues.
CONCEPT: Human oversight is not one setting. There are three patterns. Human in the loop means a person approves before the action runs; use it for hard-to-reverse or high-impact actions such as payments, access grants and messages to customers. Human on the loop means a person monitors and can intervene; use it when actions are low risk but volume is high. Human after the fact means periodic audits of samples; use it for low-risk content.

Whatever the pattern, record the approver, the time and the evidence. Measure how often humans change or reject the system's proposals: a high change rate says autonomy should not increase yet.

Controls in Foundry support this: approval flows for risky tools, tracing for audit, alerts when outputs fail quality thresholds, and constraints and tool-access controls to limit what the agent can do.

Choose the pattern by the cost of a mistake and the volume of actions.

Q: A governance checklist for an AI application includes an incident process. According to the responsible AI guidance, which item belongs in that process when a team discovers a vulnerability in the model itself?
+ Report the model vulnerability to the Microsoft Security Response Center (MSRC) :: The governance checklist names MSRC for model vulnerabilities.
- Publish the exploit details on social media first :: This is not responsible disclosure.
- Wait for the next yearly review :: Incidents need a defined, timely process.
- Ignore it if the guardrail blocked the test prompt once :: A one-time block does not remove a vulnerability.
CONCEPT: Govern is the part of the framework that answers "who is accountable, and how do we prove it?". A practical governance checklist contains: a named owner and escalation path; documented intended use and prohibited use; evaluation results stored with the release; change control for prompts, models, tools and guardrails; access control by role, with no shared keys; an incident process, including reporting a model vulnerability to the Microsoft Security Response Center (MSRC); and periodic review, at least on every model or major prompt change.

Why write it down: when something goes wrong at night, nobody should have to invent the process. The owner knows who decides, the incident process says whom to inform, and the stored evaluation results show what was tested before release.

A common mistake is to treat the content filter as the whole program, with no owner and no review cycle.

Governance repeats for the life of the system.

Q: A Spanish-language and Vietnamese-language community app relies on Azure AI Content Safety text classifiers. The team asks how reliable they are in these languages. What is the correct guidance?
+ The classifiers are trained and tested on eight languages (English, German, Japanese, Spanish, French, Italian, Portuguese and Chinese) and may work in others with less reliability, so test your own languages :: Spanish is covered; Vietnamese needs your own testing.
- They work equally well in every language without testing :: Coverage outside the eight languages is less reliable.
- They only work in English :: Eight languages are listed.
- They cannot be used at all outside the United States :: Region is not the limit; language coverage is.
CONCEPT: Content Safety classifies text and images into four categories: hate and fairness, sexual, violence and self-harm. The text classifiers are trained and tested on English, German, Japanese, Spanish, French, Italian, Portuguese and Chinese. They can work in other languages, but with less reliability.

For a product with other languages (here Vietnamese), do not assume: build a small test set with real and adversarial examples in that language, count false blocks and misses at your chosen thresholds, and adjust thresholds by category. Consider human review for borderline cases.

Remember also that severity scales differ: text uses the full 0 to 7 scale (it can be trimmed to 0, 2, 4, 6), images use a trimmed scale of 0, 2, 4, 6, and image with text from a multimodal model uses the full 0 to 7.

Re-test after every change and keep the results.

Q: A developer holds the Foundry User role on a project. They build an agent successfully and then try to publish it as an agent application, but the action is denied. What is the least privileged role change that allows publishing?
+ Assign Foundry Project Manager on the Foundry resource :: Publishing needs at least Project Manager.
- Assign Foundry Agent Consumer :: It only allows calling agent endpoints.
- Assign Azure AI Developer :: Learn advises not using this role for Foundry projects.
- Assign Cognitive Services Contributor :: Older Cognitive Services roles are not recommended for Foundry projects, except Usages Reader for quota.
CONCEPT: Foundry roles divide duties. Foundry Agent Consumer calls published agent endpoints only (a good fit for apps and end-user service principals). Foundry User builds and develops in a project, with reader access. Foundry Project Manager builds, publishes agents and assigns Foundry User to others. Foundry Account Owner creates accounts and projects and manages models but cannot build in projects. Foundry Owner has all rights.

Publishing creates a stable endpoint and a distinct agent identity, so it is a more privileged act than building. It needs at least Project Manager on the Foundry resource.

Do not use the older Cognitive Services roles (except Usages Reader for quota) or Azure AI Developer for Foundry projects. Keys bypass role-based access control, so prefer Microsoft Entra ID.

After publishing, reassign the access the new agent identity needs: the permissions of the shared project identity do not transfer.

Q: A team deletes a Foundry project that contained the shared project identity and several unpublished agents, and separately deletes one published agent application. Which statement describes what is removed?
+ Deleting a project removes its blueprint and shared identity; deleting an agent application removes its distinct identity :: These are the documented lifecycle effects.

Q: A memory store keeps both `user_profile_enabled` facts and `chat_summary_enabled` summaries for an assistant. Which TWO statements about how they should be retrieved are correct?
+ User profile items (preferences and facts) are retrieved once at the start of a conversation :: They are stable facts that personalize the whole conversation.
+ Chat summaries are retrieved dynamically, based on the current conversation :: They depend on the topic being discussed.
- Both types must be retrieved at the end of every conversation only :: This does not match the guidance.
- User profile items should be re-extracted on every message and never stored :: The store keeps them for later retrieval.
- Chat summaries are retrieved once at deployment time of the model :: They are retrieved per conversation, not at deployment.
CONCEPT: A memory store keeps durable knowledge that an agent extracts from conversations. After a conversation the system extracts items worth keeping, consolidates duplicates and conflicts with a language model, stores them partitioned by scope, and retrieves them at run time through the memory search tool or the store APIs.

Creating a store needs a chat model deployment and an embedding model deployment. Use one store per agent, set `scope` to `{{$userId}}` for per-user isolation, and set `default_ttl_seconds` for retention.

Memory is Preview, so check current limits.

Q: A Foundry orchestrator agent must call another team's agent that exposes an A2A endpoint. In the setup, what is the first step?

Q: A developer uses the Microsoft Agent Framework and marks a refund function with `@tool(approval_mode="never_require")`, copied from a quickstart. Before production, a reviewer asks for human-in-the-loop control on refunds. What should change?
+ Use `always_require` for tools that change data, so a person approves each call :: Learn's sample uses never_require for brevity and says to use always_require in production for human-in-the-loop.
- Keep `never_require` and add a sentence to the prompt asking the model to be careful :: A prompt does not enforce approval.
- Remove the refund tool and ask users to refund manually :: This removes the capability instead of controlling it.
- Increase `max_output_tokens` :: Output length does not control approval.
