Q: Your company runs an internal HR question-and-answer bot. It is used only during office hours, traffic is low, and bursts are unpredictable. There is no data residency requirement. The team wants to pay only for what it uses. Which deployment type should you choose?
+ Global Standard (pay-per-token) :: Standard deployments bill per token with no commitment, Global Standard is the documented default, and idle time costs nothing. That fits low and spiky traffic.
- Provisioned (PTU) :: Provisioned capacity is billed per PTU per hour even when idle and is sized for the peak, so most of it would be wasted on low, bursty traffic.
- Batch :: Batch is asynchronous with a 24-hour target. It cannot serve an interactive chat bot.
- Developer :: The Developer type is meant for evaluating fine-tuned models, has no SLA and a 24-hour lifetime. It is not for a production bot.
CONCEPT: A deployment type decides how the model is hosted, how you are billed, and where the data may be processed. Think of it as choosing how to buy electricity.

Standard (pay-per-token) is like a normal meter: you pay only for the tokens you send and receive, and nothing when the app is idle. It shares capacity with other customers, so it is best effort, which is fine for variable or low traffic. Provisioned (PTU) is like renting a dedicated generator: you reserve capacity and pay every hour whether or not anyone uses it, in return for predictable latency. Batch is for large offline jobs with a 24-hour target and a discount. Developer is only for evaluating fine-tuned models, with no SLA.

Global means the request may be processed in any region, which is the cheapest and most available routing. Data Zone and Regional restrict where processing happens.

How they relate: first decide the traffic shape (spiky and low, or steady and high), then the residency rule, then pick the type. An office-hours bot with no residency rule is a spiky, low-volume case, so pay-per-token Global Standard has zero idle cost.

Q: An application calls a reasoning model through the Responses API with `max_output_tokens=2000`. The input is short, but responses come back with status `incomplete` and an empty `output_text`. What should you do first?
+ Raise `max_output_tokens`, because hidden reasoning tokens count toward the cap :: Reasoning tokens are billed as output and share the output budget with the visible answer. If reasoning alone uses the 2,000 tokens, no answer is produced. Learn suggests reserving a large budget first and tuning down from measured `reasoning_tokens`.
- Add "think step by step" to the prompt :: Classic chain-of-thought prompting is not recommended for reasoning models and does not free any output budget.
- Lower the temperature :: Temperature does not change how many reasoning tokens consume the output cap.
- Ask the model to print its raw reasoning so you can debug :: Extracting raw reasoning by prompting is unsupported, may violate the Acceptable Use Policy and can lead to throttling. Use the reasoning summary setting instead.
CONCEPT: A reasoning model "thinks" before it answers. That thinking is made of reasoning tokens. You do not see them in the output, but the service counts them as output tokens.

`max_output_tokens` is a cap on all output tokens together: reasoning tokens plus the visible answer. If the model spends the whole cap on thinking, generation stops with status `incomplete` and there is no visible text. This is why a short prompt can still produce an empty answer: the input size is not the problem, the output budget is.

Fix it by raising the cap (leave generous headroom, often thousands of tokens) or by lowering the reasoning effort so the model thinks less. You can confirm the diagnosis in the usage details, where the reasoning token count is close to the cap.

How it relates: chat models spend almost all of the cap on visible text, so people carry that habit to reasoning models and set it too low. Techniques like "think step by step" or asking for raw reasoning are not needed and are not recommended for reasoning models.

Q: A compliance team requires that a Foundry resource cannot be reached over the public internet. Applications in a virtual network and users on-premises (over VPN) must still be able to call it. Which configuration meets the requirement?
+ A private endpoint for the resource in your virtual network, with public network access set to Disabled :: A private endpoint gives the resource a private IP in your VNet, works from peered networks and from on-premises over VPN or ExpressRoute, and disabling public access removes the internet path.
- A service endpoint on the application subnet with a firewall rule :: The resource keeps its public IP and DNS still resolves to it. Service endpoints are not reachable from on-premises by default.
- An IP firewall that allows only the corporate egress addresses :: The endpoint is still publicly addressable. An allow list restricts callers, but the service is not private.
- Application Gateway with WAF in front of the resource :: A gateway adds a public front door. It does not make the resource itself private.
CONCEPT: Azure services are reachable by default through a public endpoint. Network isolation means giving the service a private path and turning the public path off.

A private endpoint creates a network interface with a private IP address from your virtual network and connects it to one specific resource (Azure Private Link). Names such as `myresource.cognitiveservices.azure.com` then resolve to that private IP. Once it works, you set public network access to Disabled, so the public endpoint stops answering. Traffic from the virtual network, and from on-premises networks connected through VPN or ExpressRoute, can reach it; the internet cannot.

A service endpoint is different. It keeps the public IP and only tells the service to accept traffic that comes from a given subnet. An IP firewall allows listed public addresses. Application Gateway with WAF protects web apps, not the access path to a Foundry resource.

Memory aid: a private endpoint is a private door built inside your own building; a service endpoint is a guest list at the public front door.

Q: You create private endpoints for a Foundry resource and an Azure AI Search service and disable public access. From a VM in the virtual network, `nslookup` still returns public IP addresses for both service names and calls fail. What is the most likely cause?
+ The private DNS zones are not linked to the virtual network (or a custom DNS server does not forward to 168.63.129.16) :: Private endpoints only work when names resolve to the private IPs. That needs the `privatelink` DNS zones linked to the VNet, or a forwarder to the Azure DNS virtual server.
- The agent subnet is not delegated to `Microsoft.App/environments` :: Delegation affects provisioning of the agent runtime subnet. It does not change how names resolve.
- Key-based authentication is disabled on the resource :: That would produce 401 or 403 errors after a successful connection, not wrong DNS answers.
- The network security group blocks outbound port 443 :: A blocked port causes timeouts. It does not change the IP address that a name resolves to.
CONCEPT: A private endpoint only works if the name resolves to the private IP. Name resolution is DNS, and this is the most common reason private networking "does not work".

When you create a private endpoint, Azure expects a private DNS zone for that service, for example `privatelink.cognitiveservices.azure.com` or `privatelink.search.windows.net`. The zone holds an A record that maps the service name to the private IP. The zone must be linked to the virtual network, otherwise machines in that network keep asking the normal public DNS and get the public IP back. If your network uses a custom DNS server, it must forward queries to Azure DNS at 168.63.129.16 so that private zones are consulted.

How to check: run `nslookup` from a machine inside the network. A private IP (for example 10.x.x.x) is good. A public IP means the zone link or the forwarder is missing.

The other options are real settings but do not explain a public answer from `nslookup`: delegation is for the agent subnet, key-based auth is about credentials, and an NSG block would not change DNS answers.

Q: A team wants to improve the quality of an assistant and has listed four options. According to the recommended improvement ladder, in which order should they try them?
+ Improve the prompt, ground the answers with retrieval, choose a better or larger model, then fine-tune :: Climb one rung at a time and measure after each. Fine-tuning costs training and hosting and must be redone when the base model changes, so it is the last rung.
- Fine-tune, then ground with retrieval, then improve the prompt, then change the model :: Fine-tuning first is the most expensive and least flexible option, and it cannot add private facts reliably.
- Choose a larger model, fine-tune, improve the prompt, then ground with retrieval :: A bigger model costs more per token and does not fix missing private knowledge. Cheap changes come first.
- Ground with retrieval, fine-tune, choose a larger model, then improve the prompt :: The prompt is the cheapest lever and should be tuned first. Fine-tuning comes after the model choice, not before it.
CONCEPT: Quality problems are fixed cheapest-first. The recommended improvement ladder moves from the cheapest, fastest and most reversible change to the most expensive one.

1. Improve the prompt. It costs nothing but time, you can test it in minutes, and it fixes many problems such as format, tone and missing instructions.
2. Ground the answers with retrieval (RAG). If the model lacks facts, give it your data at question time. This fixes stale or private knowledge without changing the model.
3. Choose a better or larger model. It costs more per call and adds latency, so use it when the first two steps are not enough.
4. Fine-tune. It needs labeled data, training time and ongoing maintenance, and it teaches style or behavior, not new up-to-date facts.

Why this order: each later step is slower, costlier and harder to undo. Teams that start with fine-tuning often discover that a better prompt or retrieval would have solved the issue.

Q: A chat application receives HTTP 429 responses from a standard deployment during traffic peaks. Which TWO actions should you take?
+ Retry with exponential backoff and honor the `Retry-After` header :: 429 means TPM or RPM was exceeded. Waiting longer after each failure and respecting `Retry-After` is the documented client behavior.
+ Ramp load up gradually and give the deployment more quota :: Sharp jumps in load trigger throttling. More quota (moved from an unused deployment or by request) raises the limit itself.
- Retry immediately in a tight loop until the call succeeds :: This adds load while the limit is still exceeded, so it prolongs the throttling.
- Disable content filtering to reduce latency :: Content filtering is not the cause of 429 and removing it breaks safety requirements.
- Increase the client timeout to 29 minutes :: A longer timeout does nothing about a rate limit. Timeouts are for slow responses, not for 429.
CONCEPT: HTTP 429 means "too many requests": you went past a rate limit on requests or tokens per minute. It is an expected, temporary signal, not a bug.

The documented response has three parts. First, retry with exponential backoff: wait a short time, then double the wait after each failure, and add a little random jitter so many clients do not retry at the same instant. Second, honor the `Retry-After` header, which tells you how long the service wants you to wait. Third, avoid sharp jumps in load by ramping traffic up gradually, and if the real demand is higher than your limit, request more quota.

What does not help: retrying immediately in a loop adds load and keeps you throttled; turning off content filtering is unrelated to rate limits; a longer client timeout only makes the client wait longer for the same limit.

Memory aid: when a shop says "queue is full, come back in 30 seconds", you wait and come back politely, you do not run in circles at the door.

Q: You run a safety evaluation with 300 adversarial prompts. The Violence evaluator uses the default threshold of 3, and a case passes when its score is less than or equal to the threshold. Nine outputs score 4 or higher, and three outputs score exactly 3. The release rule says the defect rate must be 2% or lower. What is the result?
+ The defect rate is 3% (9 of 300), so the release gate fails :: A defect is a score above the threshold. Scores of exactly 3 pass, so only the nine outputs at 4 or higher count: 9 / 300 = 3%.
- The defect rate is 4% (12 of 300), so the release gate fails :: This wrongly counts the three outputs with score 3. A score equal to the threshold passes.
- The defect rate is 1% (3 of 300), so the release gate passes :: This counts only the outputs at the threshold and ignores the nine that exceed it.
- A defect rate cannot be computed without human labeling :: The evaluator already returns a score per case, so the rate is computed from those scores and the threshold.
CONCEPT: A defect rate is the share of test cases that fail the quality bar: defects divided by total cases.

Safety evaluators for harm categories (Violence, Sexual, Self-harm, Hate and unfairness) return a severity score from 0 to 7. The default threshold is 3, and a case passes when its score is less than or equal to the threshold. So a score of exactly 3 still passes, and only scores of 4 or higher are defects.

Here: 9 outputs scored 4 or higher, so 9 defects out of 300 cases. 9 / 300 = 0.03, which is 3%. The three outputs at exactly 3 pass and must not be counted. The release rule allows 2% or lower, so 3% fails the gate.

The most common mistake is to count the boundary value as a failure (12 of 300 = 4%). Always read whether the rule says "less than" or "less than or equal to". Evaluator output can be computed automatically, so no human labeling is needed to get the number.

Q: A trace of a support agent shows that for the question "Where is my order 4711?" the agent never called the `get_order_status` tool and answered generically. The tool is attached to the agent. What should you do?
+ Improve the tool description and the agent instructions so the model selects the tool, then re-evaluate with a tool selection evaluator :: When an expected tool is never called, the agent chose not to use it. Clearer names, descriptions and instructions are the first fix, and evaluators confirm the change.
- Increase the temperature so the agent explores more tools :: Randomness does not make a model understand when a tool applies and lowers consistency.
- Enable spillover to a standard deployment :: Spillover handles capacity limits. It has no effect on tool selection.
- Raise `max_output_tokens` :: Output length is not the problem. The tool was never requested.
CONCEPT: A trace is a recorded timeline of one request: each model call, each tool call with its arguments and result, and timing. It is the first place to look when an agent behaves oddly.

An agent chooses tools by reading the tool name, the description and the parameter descriptions, together with the agent instructions. If the model never calls `get_order_status`, the usual cause is that the description is vague ("handles orders") or the instructions do not say when to use it. The fix is to write a clear description ("Returns the shipping status of one order. Use when the user asks where an order is"), add a line in the instructions, and then measure again with a tool selection evaluator on a set of test questions.

Why the other options fail: temperature only adds randomness; spillover is a capacity feature for provisioned deployments; and `max_output_tokens` limits answer length, not tool choice.

How it relates: tracing shows the symptom, evaluators confirm and measure it, and prompt or description changes are the treatment.

Q: A GitHub Actions workflow that deploys agents runs on GitHub-hosted runners. It fails with 403 and connection errors against a Foundry resource that uses private endpoints and has public access disabled. The same commands work from a jump box inside the network. What should you do?
+ Run the job on a self-hosted runner inside the virtual network :: A private Foundry blocks data-plane calls from public runners. A runner that has a route to the private endpoint can reach it.
- Re-enable public network access on the resource :: This removes the isolation the security requirement asked for.
- Replace Microsoft Entra authentication with an API key :: A key does not help when the network path is blocked, and keys bypass role-based access control.
- Add retry with exponential backoff to the deploy step :: Retries cannot fix a network path that is blocked by design.
CONCEPT: Azure resources have a control plane and a data plane. The control plane creates and configures resources (through Azure Resource Manager). The data plane is what you call to use the resource: create agents, upload files, send prompts.

When a Foundry resource has private endpoints and public access disabled, the data plane is reachable only from inside the connected network. A GitHub-hosted runner is a machine on the public internet, so its data-plane calls fail with 403 or connection errors, while a jump box inside the network works. The fix is a self-hosted runner (a VM, container or scale set that you register with GitHub) placed in or peered to the virtual network, with private DNS resolving the private endpoints.

Other options do not fit: enabling public access removes the isolation you were asked to keep; an API key changes authentication but not network reachability; and retries cannot fix a route that does not exist.

Memory aid: the building is locked from the street, so the delivery person must be inside the building (self-hosted runner) to reach the room.

Q: Your subscription has enough Provisioned Throughput quota for 100 PTUs in a region. Creating a 50-PTU provisioned deployment fails with an insufficient capacity error. What explains this, and what should you do?
+ Quota is only a limit on what you may deploy; real capacity can be short. Try fewer PTUs, another region, or retry later :: Having quota does not guarantee capacity. Capacity is allocated when the deployment is created, and the failure means none was available at that moment.
- You must request a quota increase :: Quota is already sufficient. More quota would not create capacity.
- Buy a one-year reservation first so the capacity is guaranteed :: A reservation is a billing discount and does not guarantee capacity. Create the deployment and confirm capacity before buying.
- Switch the deployment to hourly billing :: The billing method does not affect whether capacity can be allocated.
CONCEPT: Two ideas are easy to mix up: quota and capacity.

Quota is a limit that Azure gives your subscription: "you may deploy up to 100 PTUs in this region". It is a policy number and it costs nothing. Capacity is the real hardware that the region has available at this moment. Demand changes during the day, so the capacity can be lower than the sum of everyone's quotas.

A provisioned deployment reserves real capacity, so creation can fail with an insufficient capacity error even when you have quota. The practical responses are to ask for fewer PTUs, try another region or a Global or Data Zone type, or retry later. A quota increase does not help because you already have enough quota.

A reservation is a billing discount for committing to PTUs for a period. It does not guarantee capacity, so the correct order is: create the deployment first to prove capacity exists, then buy the reservation.

Q: The security team wants to audit which identity called which model deployment and when, query the history with KQL, and make no code changes in the applications. What should you configure?
+ A diagnostic setting on the Foundry resource that sends the log categories (such as RequestResponse and Audit) to a Log Analytics workspace :: Platform logs are routed with a diagnostic setting and queried with KQL. No application change is needed.
- Metrics explorer charts on the resource :: Metrics show aggregated numbers (tokens, calls, status codes) but not the per-request detail needed for an audit trail.
- OpenTelemetry tracing added to each application :: Tracing needs instrumentation code, which the requirement rules out, and it is aimed at debugging runs.
- An evaluation run on production traffic :: Evaluations score quality and safety. They do not record who called a deployment.
CONCEPT: Azure produces two kinds of monitoring data: metrics (numbers over time, such as token counts) and resource logs (records of events, such as who called what). Auditing "who called which deployment and when" needs logs.

Foundry Models resources write logs in categories such as RequestResponse, Trace and Audit. By default they go nowhere. A diagnostic setting is the routing rule that sends chosen categories to a destination: a Log Analytics workspace (query with KQL), a storage account (cheap archive) or Event Hubs (streaming). It is configured on the resource, so applications do not change at all.

Why the other options fail: metrics explorer shows aggregated numbers, not individual calls with identities; OpenTelemetry tracing needs code changes in each app and shows app-level behavior; an evaluation run scores quality, not access.

How it relates: logs answer "who and when" for security, traces answer "what happened inside one request" for debugging, and evaluations answer "how good" for quality.

Q: An agent can issue payments of any size to suppliers. Payments cannot be reversed. The risk team asks for a human oversight pattern. Which pattern fits best?
+ Human in the loop: a person approves each payment before it is executed :: The action is high impact and hard to reverse, so approval must happen before the action. Record the approver, the time and the evidence.
- Human on the loop: a person monitors a dashboard and intervenes if needed :: Monitoring after the fact is too late for an irreversible payment.
- Human after the fact: audit a sample of payments each month :: Sampling later detects problems but cannot prevent a bad payment.
- No human step, because a guardrail already scans the output :: A content guardrail checks harmful content, not whether a payment is allowed.
CONCEPT: Human oversight patterns differ by how early the person acts.

Human in the loop means a person must approve an action before it happens. Human on the loop means a person supervises and can step in, but the system acts first. Human after the fact means people review results later, for example by sampling.

Choose by the cost of a mistake. A payment that cannot be reversed is high impact and irreversible, so the approval must come before execution: human in the loop. Monitoring a dashboard (on the loop) or a monthly audit (after the fact) would discover a bad payment only after the money has left.

A guardrail is a different layer: it detects harmful content or attacks in text, but it does not know your payment policy. Business limits belong in the tool code and the approval step, not in a content filter.

Memory aid: in the loop = signature before the cheque is sent; on the loop = watching the cameras; after the fact = checking the books at month end.

Q: A model provider announces a new version of the model used by a production feature that parses the model output as strict JSON. How should you adopt the new version?
+ Keep the current version pinned, deploy the new version beside it, evaluate both on the same golden dataset, then switch traffic by configuration :: Pinning avoids silent behavior changes. A side-by-side evaluation checks quality, safety, latency and cost before the switch, and the old deployment stays for rollback.
- Enable automatic upgrade so the deployment follows the latest version :: An automatic upgrade can change tone or format and break the JSON parser without any test.
- Replace the production deployment in place on Friday and watch the logs :: This skips evaluation and gives no rollback path.
- Delete the old deployment as soon as the new one is created :: Without the old deployment you cannot roll back if the evaluation reveals a regression.
CONCEPT: A model deployment is tied to a model name and a version. New versions can change tone, formatting, tool use and, for strict parsers, the exact shape of the output. A change you did not test is a production risk.

Safe adoption has four steps. Pin the current version, so nothing changes by itself (set the upgrade option to no auto-upgrade). Deploy the new version beside the old one as a separate deployment. Run both on the same golden dataset (a fixed set of representative questions with expected results) and compare the scores, including the check that the output still parses as JSON. If the new version passes your release gate, switch traffic by configuration, and keep the old deployment for a while so rollback is a configuration change.

Why the others fail: automatic upgrade lets an untested version reach users; replacing in place on Friday has no comparison and no quick rollback; deleting the old deployment removes your safety net.

Q: A finance application must read supplier invoices and return the invoice number, due date and total for each file, with a confidence score for every field. Which choice follows the rule "use the narrowest service that meets the requirement"?
+ Document Intelligence prebuilt invoice model, or a Content Understanding analyzer with field extraction :: Both are purpose-built for field extraction from documents and return structured values with confidence.
- A general chat model prompted with the page images :: A model can read pages, but fields drift between calls and there is no built-in confidence per field.
- Azure Language named entity recognition :: NER works on text and returns generic categories. It does not know invoice fields and cannot read scanned files.
- Azure Translator document translation :: Translation changes the language of a document and does not extract fields.
CONCEPT: The rule "use the narrowest service that meets the requirement" means choosing the most specialized tool that fully covers the need, because it is usually cheaper, faster, more predictable and easier to govern than a general model.

For invoices the need is: known fields (invoice number, due date, total), structured output, and a confidence score per field. Document Intelligence has a prebuilt invoice model that returns exactly these fields with confidence and the location of each value. Content Understanding can do the same with a field-extraction analyzer, and also adds more flexible schemas.

A general chat model reading page images can also extract fields, but it is less deterministic, gives no built-in per-field confidence, and costs more tokens. Azure Language named entity recognition finds generic entities in text, not invoice fields. Translator translates; it does not extract.

Memory aid: use a screwdriver for a screw. A multi-tool works, but the screwdriver is faster and fits better.

Q: An app uses `AIProjectClient` with the project endpoint. Chat calls work, but a call that creates embeddings through the same endpoint fails. What should you do?
+ Create the embeddings through the OpenAI-compatible endpoint `https://<resource>.openai.azure.com/openai/v1/` :: The project endpoint does not currently route embedding requests, so embeddings use the `/openai/v1` endpoint.
- Convert the project to a hub-based project :: Hub-based projects are the classic experience, and the current guidance targets Foundry resources and projects.
- Switch the embedding deployment to Provisioned :: The deployment type does not change which endpoint routes embedding calls.
- Grant the Foundry Project Manager role to the caller :: The call fails because of routing, not because of a missing role. A role problem would give 401 or 403.
CONCEPT: A Foundry project exposes more than one endpoint, and each one speaks a different set of APIs.

The project endpoint (`https://<resource>.services.ai.azure.com/api/projects/<project>`) is used by `AIProjectClient` for project features: agents, connections, evaluations and the OpenAI-compatible client. Model calls such as chat and responses can be reached from the project client's OpenAI-compatible client. The other options are unrelated: hub-based projects are the older model, provisioned only changes billing and capacity, and Project Manager is a management role.

Q: You run this code. It returns a 404 error, although the model catalog lists `gpt-4.1-mini` and you can see it in the portal. Your deployment is named `chat-prod`.

response = openai.responses.create(model="gpt-4.1-mini", input="Hello")

What is the fix?

- Upgrade `azure-ai-projects` to the 1.x version :: The 1.x line targets Foundry classic. The error is about the name, not the package version.

This is why teams often keep deployment names generic ("chat-prod") or identical to the model name: changing the model behind a deployment name then needs no code change.

Q: A pharmacovigilance app must map free-text adverse event reports to a controlled medical vocabulary and always return JSON that matches a defined schema. Which combination should you use?
+ Few-shot examples for the vocabulary and Structured Outputs with `strict: true` for the schema :: Few-shot examples make terminology and format consistent. Structured Outputs make the output always match the JSON Schema. They solve different problems.
- JSON mode only :: JSON mode guarantees valid JSON but not your schema or your vocabulary.
- Few-shot examples only :: Examples improve consistency but cannot guarantee that every response is valid against the schema.
- Temperature set to 0 only :: Low temperature reduces variation. It does not enforce a schema or a vocabulary.
CONCEPT: Two separate needs appear here: the model must know a controlled vocabulary, and the output must follow a schema.

Few-shot examples put a handful of input and output pairs in the prompt, so the model imitates the mapping from free text to the controlled terms. They guide content, but do not guarantee the shape of the JSON.

Structured Outputs with `strict: true` constrains the response to a JSON Schema that you provide. In strict mode every property must be listed as required, additional properties are not allowed, and an optional field is written as a union with `null`.
