Q: You size a Data Zone Provisioned deployment. Peak load is 1,000 requests per minute, with an average prompt of 200 tokens and an average response of 20 tokens. For this model, one PTU provides 3,400 input TPM, the output-to-input ratio is 8, and deployments scale in increments of 5 PTUs. The model does not use normalized token accounting, and 50% of input tokens are served from the prompt cache. The formula is: Normalized TPM = Input TPM x (1 - cache rate) + ratio x Output TPM; PTUs = Normalized TPM / input TPM per PTU, rounded up to the increment. How many PTUs do you deploy?
+ 80 PTUs :: Input TPM = 200,000 and output TPM = 20,000. Normalized TPM = 100,000 + 8 x 20,000 = 260,000. 260,000 / 3,400 = 76.47, which rounds up to 80 with an increment of 5.
- 110 PTUs :: This is the result with a 0% cache rate (360,000 / 3,400 = 105.88, rounded up to 110).
- 77 PTUs :: This is the unrounded value rounded up to the next integer. The deployment scales in steps of 5.
- 60 PTUs :: This ignores the output-token weight of 8, which dominates the calculation.
CONCEPT: Provisioned deployments are sized in PTUs (provisioned throughput units). A PTU is a unit of reserved model processing capacity. To find how many you need, convert your traffic into normalized tokens per minute and divide by what one PTU can process.

Step 1: tokens per minute. 1,000 requests/min x 200 prompt tokens = 200,000 input TPM. 1,000 x 20 response tokens = 20,000 output TPM.

Step 2: the formula in the question. Output tokens are heavier than input tokens, so they are multiplied by the ratio 8. Cached input is cheaper: with a 50% cache rate only half of the input counts. Normalized TPM = 200,000 x (1 - 0.5) + 8 x 20,000 = 100,000 + 160,000 = 260,000.

Step 3: divide by 3,400 per PTU: 260,000 / 3,400 = 76.47 PTUs. Deployments scale in increments of 5, so round up to 80.

Rounding down to 77 or 75 would under-provision, and the deployment would return 429 at peak.

Q: A team wants a one-year Azure Reservation to lower the cost of a provisioned deployment that will run at high utilization. In which order should they work?
+ Create the deployment, confirm that the capacity was allocated, then buy the reservation :: A reservation is a discount on the PTU meter and does not guarantee capacity.
- Buy the reservation first, then create the deployment :: If capacity is short, the deployment fails and the reservation guarantees nothing.
- Use hourly billing and scale the PTUs up and down with the daily traffic curve :: Capacity may not be available when you scale back up, and continuous hourly billing at high use usually costs more.
- Request more quota instead of a reservation :: Quota is a deployment limit and is not a discount.
CONCEPT: An Azure Reservation is a billing commitment: you promise to pay for a quantity of PTUs for one month or one year, and in return the hourly price is lower. It changes the price meter only. It does not reserve physical capacity in the region.

Capacity is allocated when you create the deployment. If the region cannot provide enough PTUs, the deployment fails. If you had bought the reservation first, you would have paid for a discount on capacity that you cannot use.

So the safe order is: create the deployment, confirm that the capacity was allocated and the deployment works, then buy a reservation sized to the deployed PTUs. Reservations suit stable, high utilization; for uneven traffic, hourly billing with scaling can be cheaper.

Quota is also not a substitute: it is the permission to deploy, not a price discount.

Memory aid: first make sure the seat exists, then buy the season ticket.

Q: Two teams build agents on one platform. Team A's agents must not see Team B's data, and production must be isolated from experiments in quota, policy and blast radius. Which structure fits?
+ A separate Foundry resource for production and separate projects per team with project-level connections and scoped roles :: The resource is the boundary for networking, policy, RBAC and quota. Projects separate access patterns, and project-level connections avoid inheriting resource-level connections.
- One Foundry resource and one project for everything, separated by naming conventions :: Names do not enforce access. All agents in a project share one managed identity.
- One project per agent with all connections defined at resource level :: Resource-level connections are inherited by future projects.
- Separate Azure subscriptions per agent :: This is far more than the requirement needs and complicates governance.
CONCEPT: Foundry has levels of structure, and each level is a boundary for something different.

A Foundry resource is the top boundary for administration, networking, policy, quota and monitoring. A project, inside a resource, is the working area for a team: its agents, files, connections and role assignments. Agents in a project share one managed identity (until published), and connections defined at project level are visible only to that project.

To isolate production from experiments in quota, policy and blast radius, use separate resources (production versus non-production). To keep Team A away from Team B's data, use separate projects, define connections at project level, and scope roles to each project.

Naming conventions are not access control. Connections at resource level are inherited by all projects, which breaks isolation. A subscription per agent is heavy and unnecessary.

Q: An agent application uses a model deployment in a single region. During a regional incident, requests fail and nobody fails over to another deployment. What is true about Foundry in this situation?
+ Foundry does not load-balance or fail over model deployments for you; use a gateway such as API Management and Data Zone or Global deployment types :: Resilience must be designed: routing, health checks and circuit breaking in a gateway, plus deployment types that are not tied to one region.

- Provisioned deployments are always zone redundant :: Provisioned capacity gives consistent latency, not automatic failover.
- Foundry copies agents to a second region continuously :: Agent Service has no built-in backup or disaster recovery.
CONCEPT: Reliability design must be explicit in Foundry. A model deployment lives in one region. If that region has an incident, calls to that deployment fail.

Foundry does not load-balance or fail over model deployments for you, and it does not replicate agents to a second region automatically. Standard deployments do not fail over to a paired region, and provisioned deployments are not automatically zone redundant.

What you do: use Data Zone or Global deployment types, which spread processing over several regions inside the routing scope, and put a gateway such as Azure API Management in front of two or more deployments. Also keep agent definitions as code, so they can be redeployed in another region.

Q: A security review finds that agent traces in Application Insights contain customers' phone numbers and one API key that was placed in a tool argument. What should you do?
+ Redact or minimize personal data and never place secrets in prompts, tool arguments or span attributes; apply the same access control and retention as production logs :: Traces can contain user text, outputs and tool arguments, so privacy controls must be applied before data reaches telemetry.
- Turn off tracing in production :: This removes the ability to debug and does not fix the practice of leaking secrets.
- Keep the data and shorten the retention to one day :: Secrets should not be recorded in the first place.
- Move the traces to a public storage account :: This increases exposure.
CONCEPT: Telemetry is a copy of your data. Traces can include prompts, tool arguments and results, so personal data and secrets can end up in Application Insights.

The rule is data minimization and secret hygiene. Do not place secrets (API keys, tokens, connection strings) in prompts, tool arguments or span attributes at all; use managed identity or a secret store, and let the tool fetch secrets itself. Redact or avoid recording personal data such as phone numbers, or record only what you need. Treat the telemetry store like production data: restrict access with roles, set retention, and consider the same compliance obligations as for the source data. If a key has already leaked into traces, rotate it.

Turning tracing off in production gives up your best debugging tool. One-day retention keeps the data in the meantime. A public storage account is the opposite of control.

Memory aid: logs are a diary; do not write passwords in it.

Q: Which TWO statements about few-shot examples are correct?
+ They condition the model for the current call only and nothing is learned permanently :: Examples are part of the prompt, so they do not change the model.
+ The order of examples can matter, and examples should show edge cases :: Examples shape the pattern the model continues, so their choice and order affect the result.
- They permanently fine-tune the deployment :: Fine-tuning is a separate training process.
- They guarantee factual correctness of the output :: They improve format and consistency, not truth.
- They are required for reasoning models :: Classic techniques such as these are not recommended for reasoning models.
CONCEPT: Few-shot prompting adds a few examples of input and output to the prompt, so the model imitates the pattern. It is also called in-context learning.

The examples condition the model for the current call only. Nothing is stored, nothing is learned permanently, and the deployment is unchanged. That is the difference from fine-tuning, which changes the model's weights through training.

Practical points: the order of examples can influence the answer (the last examples often have more weight), and examples should include edge cases, not only easy ones, so the model sees the boundaries. Examples improve format and style but do not guarantee facts; a model can copy the format and still be wrong.

Reasoning models usually work well with short, goal-oriented prompts, and heavy few-shot prompting is not required for them.

Memory aid: few-shot is showing a new employee three sample cases before the shift. Fine-tuning is sending them to training school.

Q: A hybrid search returns three documents. Reciprocal Rank Fusion uses `score = sum of 1 / (rank + k)` with k = 60. Document A ranks 1st in the keyword list and 5th in the vector list. + B, A, C :: B = 1/62 + 1/61 = 0.03252, A = 1/61 + 1/65 = 0.03178, C = 1/63 = 0.01587. A document that is high in both lists wins.
- A, B, C :: A was first in the keyword list, but B scores higher because it is high in both lists.
- C, B, A :: C appears in only one list and scores about half as much.
- A, C, B :: B's score is not the lowest, since it ranks 1st in the vector list.
CONCEPT: Reciprocal Rank Fusion (RRF) merges ranked lists. Each document gets a score from each list where it appears: 1 / (rank + k), with k = 60 in the question. The scores are added, and documents are sorted by the sum.

Document A: 1st in keywords = 1/61 = 0.01639, 5th in vectors = 1/65 = 0.01538, sum = 0.03177.
Document B: 2nd in keywords = 1/62 = 0.01613, 1st in vectors = 1/61 = 0.01639, sum = 0.03252.
Document C: 3rd in keywords = 1/63 = 0.01587, absent from the vector list = 0, sum = 0.01587.

Order: B (0.03252), A (0.03177), C (0.01587).

Lesson: RRF rewards documents that are high in both lists. A is first in one list, but only fifth in the other, so B, which is first and second, beats it narrowly. A document found by one method only (C) still appears, but with a lower score.
