=== D1 single
Q: A client application sends requests to a model endpoint and receives HTTP 431. The network, the quota and the credentials are all fine. Which cause fits this status code?
+ The request carries more than 10 custom headers :: A request may carry at most 10 custom headers; more returns HTTP 431.
- The tokens-per-minute limit was exceeded :: That gives HTTP 429.
- The key or token is invalid :: That gives 401.
- The deployment name does not exist :: That gives a not-found style error, not 431.
CONCEPT: HTTP status codes tell you which layer failed, so learn the common ones. 401 means a bad or missing credential. 403 means valid credentials but the operation or configuration is not allowed. 429 means a rate limit (tokens or requests per minute) was exceeded. 431 means the request has too many custom headers: the limit is 10. 503 can appear during peaks, so monitor 429 and 503 together.

The 431 case is easy to cause with a gateway or a proxy that adds many tracing or routing headers. The fix is to send ten or fewer custom headers.

Other fixed limits worth remembering: 100 Foundry resources per region per subscription, 250 projects per resource and 32 model deployments per resource.

When you see an unusual status code, check the troubleshooting table before changing capacity.

Q: A team tries to create a deployment of a model with the Batch deployment type, but the type is not offered for that model in the chosen region. What is the correct way to resolve this?
+ Check the availability of the model by deployment type and region, then pick a supported type or region :: Not every model supports every deployment type in every region.
- Request a quota increase until the type appears :: Quota does not add a deployment type to a model.
- Restart the Foundry resource :: This does not change which types a model supports.
- Enable key-based authentication :: Authentication does not control available deployment types.
CONCEPT: A deployment type is a combination of billing and processing scope: Standard, Provisioned, Batch, Developer and Priority, each with Global, Data Zone or regional variants. Models differ in which combinations they support. Geography-based types usually arrive last for new models, and there is no guaranteed availability date.

When the portal or an API says the type is not available, the cause is nearly always availability, not permission or quota. The troubleshooting table lists it as "deployment type unavailable: the model does not support that type; check availability by type and region".

Check the model card's Deployments tab and the regions. Then decide: choose another type (for example Global Standard), another region, or another model.

The quota page shows the limit by scope; if it shows 0 available, move quota or request an increase. That is a different symptom.

Q: A back-end service calls a reasoning model without streaming. Complex requests fail after exactly 60 seconds with a client timeout, although the service responds correctly in tests with a longer timeout. What is the best fix?
+ Set the client timeout explicitly, since reasoning models can take much longer (up to about 29 minutes), and tune it to your traffic :: Library defaults may not match the service, and reasoning happens before the first output token.
- Switch the deployment to Batch for interactive use :: Batch is asynchronous with a 24-hour target and is not for live responses.
- Disable reasoning by lowering the temperature :: Temperature does not control reasoning, and the effort setting is the relevant control.
- Add more custom headers to keep the connection alive :: This risks HTTP 431 and does not extend timeouts.
CONCEPT: Client timeouts are your responsibility. Learn's guidance: non-reasoning streaming calls up to 60 seconds; non-streaming calls or reasoning models up to 29 minutes, set lower and tuned to your traffic. Set them explicitly, because a library default may not match the service.

Reasoning models generate and summarize all reasoning tokens before the first visible output token, so even a streaming call shows a long wait at the start. The `reasoning_effort` parameter controls how many reasoning tokens are produced, so a lower effort shortens the wait for tasks that do not need deep thinking.

To decide a good timeout, log latency percentiles for a day. Pick a value above the 95th percentile and keep user-facing interfaces responsive with progress messages.

For work that can wait, use a Batch deployment, not a longer timeout.

Q: Operations has an alert for HTTP 429 but users still report failures at peak hours that the alert does not catch. Dashboards show many 503 responses. What should the team change?
+ Monitor 429 and 503 together, and add a gateway or capacity measures for the peaks :: 503 can also appear during peaks, so throttling and overload are watched as a pair.
- Ignore 503 because only 429 is related to load :: 503 is part of the peak-load picture.
- Disable alerts to avoid noise :: This removes visibility.
- Lower the prompt length to 10 tokens :: The cause is capacity at peak, and this makes the application unusable.
CONCEPT: Two statuses show load problems. 429 means you exceeded a limit (tokens or requests per minute) and the right reaction is retry with exponential backoff, honor the Retry-After header, ramp load gradually and add quota. 503 can appear when the service is under pressure during peaks. Learn advises monitoring both together.

For production, a single deployment is not enough. Foundry does not load-balance or fail over model deployments for you. Put a gateway such as Azure API Management in front for routing, health checks and circuit breaking across deployments or regions. Prefer Data Zone or Global deployment types for resilience, use spillover from provisioned to standard, and keep models in the same region as the agents.

Metrics are in Azure Monitor: chart total calls, filter by status code and split by `ModelDeploymentName`.

Alert design: cover every status that means "user did not get an answer".

Q: An app sends a 5,000-token shared policy prefix on every request. Cache hits are high during the day, but the first request after a quiet night is slow and costly, and a staging environment in another subscription never benefits from the production cache. Which statement explains both observations?
+ In-memory prompt caches are usually cleared after 5 to 10 minutes of inactivity, and caches are not shared between Azure subscriptions :: Idle time clears the cache, and each subscription has its own cache.
- Prompt caching is permanent once a prefix is seen :: In-memory caches are cleared after inactivity and always within one hour of last use.
- Caches are shared across all subscriptions of a tenant :: They are not shared between subscriptions.
- Caching only works on Provisioned deployments :: It applies to Standard deployments as well, with a discount on cached input.
CONCEPT: Prompt caching keeps processed input tokens temporarily, so a request that starts with the same content as an earlier one is cheaper and faster. It requires a prompt of at least 1,024 tokens whose first 1,024 tokens are identical, with further hits in 128-token increments on GPT-5.5 and earlier. It changes only latency and cost, never the output.

Lifetime rules: in-memory caches are usually cleared after 5 to 10 minutes of inactivity and always within one hour of last use. Extended retention on selected models can keep prefixes up to 24 hours. Caches are not shared between Azure subscriptions.

So the first call after a quiet period is a miss, and a staging subscription warms its own cache. Check the `cached_tokens` value in `prompt_tokens_details`.

Put stable content first (system message, tool definitions, reference text) and variable content last.

Q: In a network-secured setup, the Agents page in the Foundry portal shows a timeout when loading, although the model deployments work. Which cause is most likely?
+ The portal cannot reach Azure Cosmos DB, because of a missing private endpoint or DNS configuration :: The Agents page reads agent data from Cosmos DB, and unreachable private resources cause timeouts.
- The model deployment is Global Standard :: Deployment type does not affect the Agents page.
- The agent has too many versions :: Versions do not cause a network timeout.
- The guardrail is in annotate-only mode :: Guardrail mode affects content decisions.
CONCEPT: In the standard agent setup, conversations, agent definitions and run state live in your Azure Cosmos DB account, files in Storage and vector stores in Azure AI Search. With network isolation, all of these are reached through private endpoints, and names must resolve to private IPs through linked private DNS zones.

The symptom "timeout loading the Agents page" points to Cosmos DB: either its private endpoint is missing, or the DNS zone `privatelink.documents.azure.com` is not linked, or the person's network cannot reach the private endpoint. The model deployments can still work because they use a different path.

To diagnose, run `nslookup` from a machine in the network. A private IP means DNS is right. To use the portal against a locked-down project, use a VPN gateway, ExpressRoute, or Azure Bastion to a jump box inside the network.

Name resolution failures are the most common private networking problem.

Q: Creating the capability host for a standard agent setup fails with an error about connections. The team supplied a Cosmos DB account and a Storage account. What is the most likely missing piece?
+ The Azure AI Search resource, because a network-secured standard setup requires all three bring-your-own resources :: Cosmos DB, Storage and AI Search are all needed.
- A second Foundry resource in another region :: The three data resources are required, not another Foundry resource.
- A Provisioned model deployment :: Capacity does not affect the capability host.
- A public IP address for the agent runtime :: The goal is the opposite: private networking.
CONCEPT: The standard agent setup puts your agent data in your own resources: conversations, agent definitions and run state in Azure Cosmos DB for NoSQL, uploaded files in Azure Storage and vector stores for file search in Azure AI Search. A network-secured standard setup requires all three. If one is missing, creation of the capability host fails with an error about connections.

This is listed in the troubleshooting symptoms: "Capability host creation error about connections: one of the three BYO resources is missing".

Check the list of three resources first when a creation error mentions connections.

Q: A team decommissions a test environment and tries to delete its virtual network. The delete fails because the agent subnet still has a service association link. What is the correct order of cleanup?
+ Purge the Foundry resource first, and then delete the virtual network :: Otherwise the subnet keeps the service association link.
- Delete the virtual network first and the Foundry resource afterward :: The subnet cannot be deleted while the link exists.
- Delete only the Cosmos DB account :: The link belongs to the Foundry resource, not Cosmos DB.
- Remove the private DNS zones and retry :: DNS zones are unrelated to the association link.
CONCEPT: When agent runtime is injected into a delegated subnet, the Foundry resource creates a service association link on that subnet. Azure will not delete a subnet that still has such a link.

The documented cleanup order is: purge the Foundry resource before deleting the virtual network. Deleting a Foundry resource normally soft-deletes it, so a purge is needed to release the subnet.

Remember related rules for the subnet: it is dedicated to one Foundry resource (it cannot be shared), delegated to `Microsoft.App/environments`, uses a private address range with a recommended size of /24, and must not overlap with peered networks.

When you design infrastructure as code for temporary environments, include the purge step in the teardown script so repeated create-and-destroy cycles do not fail.

Q: A new project's agents cannot use several features and fail without clear errors. The team granted the developers Foundry User, but nothing was assigned to the project's own managed identity. What should they do?
+ Give the project's managed identity the Foundry User role on the Foundry resource :: Some features fail silently when the project identity lacks this role.
- Give the developers the Owner role at subscription scope :: Developer roles do not fix a missing role for the project identity.
- Switch every connection to API keys :: Keys bypass role-based access control and are not the recommended fix.
- Delete and recreate the project :: This is unnecessary, and the new identity would again need the role.
CONCEPT: Foundry roles apply to people and also to identities used by the platform. Each project has a managed identity, and agents in the project use it to reach resources. The rule is: give the project's managed identity the Foundry User role on the Foundry resource too, or some features fail silently.

"Silently" is the key word: the portal does not always show a clear authorization error, so the symptom is features that do not work.

The roles at a glance: Foundry Agent Consumer (call agents only), Foundry User (build and test), Foundry Project Manager (publish agents and assign Foundry User), Foundry Account Owner (accounts and models) and Foundry Owner (all).

Q: A platform engineer runs `az role assignment create` to give the Foundry account's managed identity the "Cosmos DB Built-in Data Reader" role on a Cosmos DB account. The command fails to grant data access. What is the correct approach?
+ Use `az cosmosdb sql role assignment create`, because it is a Cosmos DB data-plane role, not an Azure RBAC role :: Cosmos DB data-plane roles are assigned with the Cosmos CLI.
- Retry `az role assignment create` with the Owner role :: The data-plane role is not an Azure RBAC role, so Owner does not apply.
- Enable local key authentication instead :: Keys are not the recommended approach and bypass role control.
- Assign the role to the developer, not to the identity :: The runtime identity needs the data-plane role.
CONCEPT: Azure has two layers of access control. The control plane (Azure RBAC) manages resources: creating or deleting an account. The data plane governs reading and writing the data. Cosmos DB for NoSQL has its own data-plane role system, and its roles such as "Cosmos DB Built-in Data Reader" are assigned with `az cosmosdb sql role assignment create`, not with `az role assignment create`.

For bring-your-own resources, two identities are involved. The person or pipeline that provisions needs roles such as Storage Blob Data Contributor and Cosmos DB Operator. The Foundry account's or project's managed identity needs data-plane roles at runtime. A very common failure is granting only the first set.

Symptom: provisioning succeeds, but agents fail when they try to read or write data.

Check which layer the role belongs to before choosing the command.

Q: An evaluation gate in a pipeline sometimes passes and sometimes fails for the same agent version, with a small dataset of 15 cases and an LLM judge. What is the most likely cause and the right response?
+ Judge variance with a tiny sample; run the evaluation twice and widen the dataset :: A small sample and judge variability make results noisy.
- The agent code changes every time the pipeline runs :: The version is the same, so the code does not change.
- The pipeline needs a lower threshold so that it always passes :: Lowering the gate hides regressions.
- Evaluation cannot be repeatable, so remove the gate :: Gates can be made stable with a better dataset.
CONCEPT: An evaluation gate is a pass or fail decision that blocks a release. For it to be useful it must be stable. Learn's troubleshooting lists the causes: a flaky gate comes from judge variance and a tiny sample. Most evaluators are AI-assisted, so a judge model scores each case, and a judge can vary a little from run to run.

Practical fixes: run the evaluation twice and compare, widen the dataset (keep a small fast set for pull requests and the full set for release candidates), and use confidence intervals when comparing versions. A gate should combine an absolute floor, a rule relative to the baseline, must-pass cases and a budget.

The opposite problem, a gate that always passes, comes from a dataset that is too easy or too small: add real failures from production.

Version the dataset with the code.

Q: Three months after launch, a team notices that its pipeline gate has passed on every single release, even though users report regressions. Which action addresses the root cause?
+ Add failing conversations from production as new test cases and examine the confidence intervals, because the dataset is probably too easy or too small :: Each production incident becomes a test case that the gate must pass.
- Raise the judge model's temperature to make scores vary :: Randomness makes results noisy and does not improve coverage.
- Remove the must-pass cases so the gate is simpler :: This makes the gate weaker.
- Evaluate only the first message of every conversation :: This narrows coverage further.
CONCEPT: A gate is only as good as its test data. If the dataset contains only polite, easy, familiar questions, every release looks fine. The symptom "gate always passes" in Learn's troubleshooting table has the cause "dataset too easy or too small", and the check is to add failures from production and look at the confidence interval.

Good dataset hygiene: version the dataset with the code; add every production incident as a new test case; keep a small fast set (about a dozen cases) for every pull request and the full set for release candidates; include must-pass scenarios such as a refund limit or a privacy request.

A worked example in the lesson: production task adherence is 4.6 and a candidate scores 4.4 with a 95% interval of 4.3 to 4.5. The interval lies entirely below the baseline, so the gate should fail even though 4.4 is above an absolute floor of 4.0.

Use both an absolute and a relative rule.

Q: A compliance officer asks to enable content filtering on an embedding model deployment, so that harmful input texts are blocked before they are vectorized. What is the correct answer?
+ Content filtering is not available for embedding models; screen the text earlier with Azure AI Content Safety if needed :: Learn lists embedding and time-series models as not supported for content filtering.
- Enable the Violence control on the embedding deployment guardrail :: Embedding deployments do not support content filtering.
- Convert the embedding into text and send it to the model :: Embeddings are numeric vectors and cannot be converted back to meaningful text for filtering.
- Use a Provisioned deployment, which filters embeddings automatically :: Deployment type does not add filtering.
CONCEPT: Content filtering is built into serverless model deployments and can be customized. There are exceptions that Learn calls out: filtering is not available for embedding models and time-series models. Also, if you call a serverless model through an API that is not the Azure OpenAI SDK surface, you do not get filtering unless you add Azure AI Content Safety yourself.

For an embedding pipeline, put the safety check before the embedding call: scan the text with Content Safety, or filter documents at ingestion, then embed. Remember also that retrieved text is untrusted when it later reaches a chat model, so the indirect attack control at the tool response point and prompt structure matter there.

An embedding is just a list of numbers, so there is no readable output to filter.

Plan filtering at the stages that produce or consume text: ingestion, prompt, tool response and output.

Q: A function tool call returns `arguments` that fail JSON parsing in the application, or contain values of the wrong type. Which TWO actions follow the troubleshooting guidance?
+ Fix the parameter types and mark fields as required in the schema, and use `strict: true` :: A precise schema with required fields and strict mode reduces malformed arguments.
+ Handle parse errors in the application and treat arguments as untrusted input :: The app must be defensive, because the arguments are produced by a model.
- Remove the schema so that the model has more freedom :: The schema is what guides the arguments.
- Ignore errors and pass the raw string to the function :: This invites failures and security problems.
- Switch to a model without tool support :: The model would not call tools at all.
CONCEPT: In function calling, the model returns a `function_call` item with a name, `arguments` as a JSON string and a `call_id`. Your application parses the string, runs the function, and sends back a `function_call_output` with the same `call_id`.

Learn's troubleshooting table for argument problems: arguments not valid JSON means a schema mismatch, so fix types and `required` fields and handle parse errors; required fields missing means the schema does not enforce them, so add `required` and use `strict: true`; wrong parameters mean an ambiguous description, so clarify with examples.

The schema should also set `additionalProperties: False`. Every parameter should have a clear description with an example such as "Order number, e.g. 4711".

Because the model creates the arguments, the application must validate them before use.

Q: A RAG evaluation shows high Retrieval and high Groundedness scores, but the Relevance score is low: answers are faithful to the context yet do not address what the user asked. Which fix fits best?
+ Improve query understanding, for example rewrite the query with conversation history, and tighten the prompt so the model answers the actual question :: Low relevance means the model answers a different question.
- Raise `top_k` to 100 for completeness :: That addresses missing facts, not answers to the wrong question.
- Lower the embedding dimensions :: Dimensions affect vectors and not the question being answered.
- Replace the semantic ranker with BM25 only :: Ranking is not the issue here.
CONCEPT: The score pattern across evaluators tells you where the system fails. Retrieval asks whether the retrieved chunks are relevant to the query. Groundedness asks whether the answer stays inside the context (precision). Relevance asks whether the answer addresses the question. Response Completeness asks whether expected facts are missing (recall).

Here retrieval and groundedness are high, so the right content was found and the answer follows it. Low relevance means the answer addresses something else. A typical cause is that a follow-up such as "and for phones?" was searched without context, or the prompt does not tell the model to focus on the user's question.

Fixes: fold conversation history into the query, rewrite the query, and refine the prompt.

Compare with other patterns: retrieval low means better chunking, hybrid search or OCR; retrieval high but groundedness low means a stricter prompt or lower temperature; groundedness high but completeness low means higher `top_k`.

Q: A test shows that the correct document is retrieved by hybrid search but sits at position 30, so it never reaches the model's prompt. The team wants to improve ordering without changing the content. Which step addresses this?
+ Add the semantic ranker, which rereads the top results and reorders them by how well they answer the question :: Reranking moves the best answer to the front, provided it is within the first 50 results.
- Add more chunks to the prompt until position 30 fits :: This raises cost and noise.
- Change the embedding model without re-embedding :: This breaks vector consistency.
- Remove the keyword part of the hybrid query :: This reduces exact matching and does not specifically fix ordering.
CONCEPT: Retrieval produces a candidate list, and rank decides what reaches the model. In hybrid search, Reciprocal Rank Fusion merges the keyword list and the vector list by rank position. The result can still have the best answer at position 30.

The semantic ranker is a second-stage reranker. It takes the top 50 results, builds a summary of each from the fields of the semantic configuration (title, keywords, content), and scores each from 0 to 4 for how well it answers the query. The best ones move to the front.

Its limit is important: it only reorders what retrieval already found. If the right document is not in the first 50, it cannot rescue it, which is why guidance sets the vector `k` to 50.

To measure the benefit, compare the rank of the right document before and after, using Document Retrieval metrics on a labeled set.

Q: A hybrid search with a security filter returns zero results for one user, although the same query without the filter returns relevant documents. The filter uses a `groupIds` field populated at ingestion. What should the team verify first?
+ That the access information was collected at ingestion and the filter expression matches the stored field values for that user :: A filter that matches nothing removes all results, so the permission field and expression are the first suspects.
- That the semantic ranker is disabled :: The ranker does not remove documents because of a filter.
- That the embedding model has more dimensions :: Dimensions do not decide filter matches.
- That the index uses exhaustive KNN :: The algorithm does not change filter logic.
CONCEPT: In the online RAG pipeline, retrieval runs a keyword query and a vector query in parallel, then applies filters (department, region, date) and security trimming so that only chunks the user may read are returned. Each method returns a ranked list.

A common failure is "filters removing everything". The cause is usually in the data: access information (who may read each chunk) must be collected at ingestion, because it cannot be added later without re-reading the source. If the field is empty or has different values than the filter expects, the result is empty.

How to check: run the query without the filter, inspect a few documents' permission fields, and run the filter alone in the portal before involving any language model.

Filters and facets work in hybrid queries. With the semantic ranker you probably want post-filtering; test both.

Q: A team embeds whole 15,000-token chapters using `text-embedding-3-small` and notices that content at the end of every chapter is never found, with no error. What is the cause?
+ The model's input limit is 8,191 tokens, so longer text is cut off silently; chunk the content before embedding :: Text over the token limit is truncated, so the end never influences the vector.
- The model refuses long inputs with a clear error message :: The failure is silent in this scenario.

Q: A developer sends SSML for text to speech that contains the text `Terms & Conditions apply`. The synthesis request fails with an XML error. What is the likely cause?

CONCEPT: SSML (Speech Synthesis Markup Language) is XML that controls speech: rate, pitch and volume with `prosody`, pauses with `break`, pronunciation with `phoneme` and lexicons, voice or style changes inside one document, and the language for multilingual voices.

Q: A blob index uses one-to-many indexing, where one blob creates many search documents. The team configures a soft-delete deletion detection policy, but deleted blobs' child documents remain. What is the documented limitation and the workaround?

- The policy needs a higher indexer schedule :: Schedule does not change the limitation.

CONCEPT: Indexers detect new and changed blobs automatically by comparing the last-modified timestamp, but they do not detect deletions.
